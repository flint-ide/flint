## Editor and navigation

### Tabs

Files, terminals, agent chats, SQL consoles and diffs share one tab area, with file-type icons. A file opened from a terminal appears next to it, and `⌘[` goes back to the terminal (navigation history works like IntelliJ). `⌘J` toggles between the terminal and the last file. `+` opens a terminal, an agent chat or a SQL console.

### Terminal

- A real PTY (`creack/pty`) running your login shell with your `PATH`, rendered with WebGL. Multiple tabs.
- `⌘`+click on `path:line` in agent output opens the file at that line.
- A relative path is looked up in the folder the shell is in now (it may have `cd`-ed away from where the terminal started), then the folder the terminal started in, its workspace folder and the other workspace folders; the first that has the file opens. If none has it, the first is opened and its error shows. Paths in run consoles are tried against the run's folders (`openRunLink`); CI logs map paths in Go.
- Shift+Enter inserts a newline in claude/codex prompts.
- On macOS `⌘←` / `⌘→` move to the start / end of the line (sent as Ctrl+A / Ctrl+E) and `⌘↑` / `⌘↓` scroll to the top / bottom of the scrollback.
- Selected output can be sent to the agent chat as a code block with `⌘L` or right-click → *Send to agent*.

### Background terminals

- Off by default. **Settings ▸ Terminal ▸ Keep terminals running when Flint closes** (`sessions.background`) runs terminals in a separate Flint process, the background host, instead of inside the window. The change applies the next time Flint starts.
- With it on, closing the window and Quit (`⌘Q`) detach: Flint exits and the shells, and whatever runs in them (a build, a server, the claude TUI), keep running. On the next start a saved terminal tab whose shell still runs reattaches: the host replays the output it kept (`sessions.replayKiB`, 1 MiB per terminal by default, at most 8 MiB) and a full-screen program redraws. Nothing is typed into it and no new shell starts. A saved terminal whose shell is gone comes back as before, as a new shell with its old output dimmed above.
- Closing a terminal tab ends its shell, as without background terminals. **Quit and Stop Background Sessions** (app menu on macOS, File menu on Linux, next to Quit) ends every background shell and the host, then quits; with the setting off the item is hidden.
- Terminals the host runs that no tab claims (the session file was lost, or they belong to another folder) are never opened or ended on their own: Flint says so once, and **Show Background Terminals…** in the command palette lists them with Attach (opens a tab) and End.
- What does not survive: Docker and extension shells (they need the window), the host itself (if it crashes or the computer restarts, the shells end and the tabs come back as new shells) and terminals of a host from another Flint version if you choose **Restart Background Sessions** when Flint asks. Choosing **Keep Them** leaves that host running and this run's terminals run inside Flint.
- If the background host cannot be started or reached within a few seconds, terminals run inside Flint for that run and Flint shows why. If the connection breaks while Flint is open, Flint reconnects once and reattaches every terminal where it left off; a terminal the host no longer has, or a second failure, shows a message on its tab and ends there.
- Agent chats are not covered yet: they stay inside Flint and end when it quits, whatever the setting says.

### Remote terminals

- Terminals can run on another computer over your own `ssh`. Add machines under **Settings ▸ Machines** (id, name, target `host`, `user@host` or an alias of `~/.ssh/config`, port, command), then use **New Terminal on Machine…** in the command palette or **＋ ▸ Terminal on <machine>**. The shell starts in your home folder on that machine; nothing from the open folders (paths, environment) is sent.
- Key-based login only: Flint runs `ssh` with `BatchMode`, so it never asks for a password or a host-key question; a refused key or unknown host shows ssh's own (redacted) error on the tab and in the status bar. Flint stores no credential. Jump hosts and other keys belong in `~/.ssh/config`.
- The first time per run that Flint runs `ssh` for a machine (to connect, or for its Check) a native dialog shows the exact command line and asks. Decline and nothing connects; the tab says why.
- The machine needs Flint's headless host (`flint`, from `cmd/flint-host`). **Check** on the machine's settings runs `<command> --version` over ssh (10 s connect timeout, 20 s in all, output capped) and says: ready (version, host protocol), a different protocol, `flint` not found, or ssh's error. When Flint is missing or incompatible the page shows copyable install steps (system, download from the releases page, SHA-256 check, unpack into `~/.local/bin`, run it, set Command). **Flint installs nothing by itself.** No release publishes the archives yet: the file names (`flint-host-<os>-<arch>.tar.gz`) are where releases will publish them, so until then build one with `wails3 task host:package` (see [Development](DEVELOPMENT.md#the-headless-host-remote-machines)).
- The tab reads `<machine> ▸ <title>` with a small machine badge. While Flint connects, reconnects (backoff 1, 2, 4 … 60 s) or fails, the tab shows a banner and the status bar a "machine: connecting… / reconnecting… / connection failed" item. Output, titles, exit codes and the state of an agent CLI running in the shell (the tab badge) arrive as for a local terminal.
- Closing a tab ends its shell on the machine. Closing the window or quitting leaves the shells running there. On the next start a saved remote tab re-attaches if the machine still has the session (the machine replays what it kept); if not, or if the machine was removed from settings, the tab opens ended and says "session ended on <machine>". A restored remote tab never starts a new shell.
- Allowed in Restricted Mode: it runs nothing from the folder, like the local New Terminal command. The automatic first terminal still waits for trust.
- Remote terminals are not visible to agents' MCP tools (list or read terminals), so an agent cannot read or type into a shell on a machine.
- Out of scope: remote files, editor, git, language servers, search, port forwarding, uploads, Windows machines, automatic install or update, password or 2FA prompts, and **agent chats on a machine** (the host has no approvals, MCP tools or per-agent settings yet): there is no "agent on machine" option.

### Status of agents in terminal tabs

- An agent CLI running in a terminal tab can report what it is doing with an escape sequence, and the tab then shows a small badge (working, waiting, done) and the agent is listed in the Agents panel (kind *terminal*, same order and "needs you" rules: waiting needs you, done counts as finished until you show the tab). *list_agents* reports it with `kind: "terminal"`.
- What Flint reads (`internal/terminal/agentstate.go`, in the output stream, which is passed to the screen unchanged): Flint's own `ESC ] 6977 ; state=<working|waiting|done|idle> BEL` (or `ESC \` as terminator); the desktop-notification sequences `OSC 9;<text>` and `OSC 777;notify;…` as *waiting* (`OSC 9;4` progress and the other ConEmu `9;<number>;…` forms are not notifications and are ignored); and the shell prompt coming back after the program that reported a state, as *idle* (the badge and row disappear). Sequences are at most 512 bytes; anything else is ignored. 6977 was chosen because none of the private OSC numbers of the common terminals (iTerm2 1337, kitty 99 and 5522, VTE 3008, WezTerm, Ghostty, foot, VS Code 633, FinalTerm 133) uses it; that check is from their documentation, so the payload is matched exactly.
- **New Claude Terminal** (command palette; deliberately not the default of *New Terminal*) opens a terminal and types `claude --settings '<config dir>/agent-hooks/claude-status.json'`. The file holds Claude Code hooks (`UserPromptSubmit` and `PreToolUse` → working, `Notification` → waiting, `Stop` → done) whose commands write the sequence to `/dev/tty`. Flint writes it only for a trusted folder and rewrites it when its content differs. Flint never modifies `~/.claude/settings.json` or any other file you own. **Settings ▸ Agents ▸ Claude in a terminal tab ▸ Copy hook snippet** copies the same hooks for you to merge into your own Claude Code settings.
- **Unverified:** whether `claude --settings <file>` *merges* its hooks with the hooks in your own settings (the CLI's help says the flag loads "more settings"; the behaviour was not exercised, because it would need a Claude Code session). If it replaced them, your own hooks would not run in terminals started with *New Claude Terminal*; use the copied snippet instead. A terminal restored after a restart resumes Claude without `--settings`. What was verified: a hook-like command (a child of the foreground program with its output piped) can write the sequence to `/dev/tty` and Flint reads it (a test); that Claude Code starts hooks that way was not.

### File tree

- Virtualized tree with selection (click, `⌘`+click, `⇧`+click, arrow keys).
- Right-click opens a context menu: New File / New Folder and Rename, edited in place (`F2` / `↵`); Move to Trash (`⌘⌫` / Delete, with confirmation, also for multiple selected items); Copy Path / Copy Relative Path; Reveal in Finder; Open in Terminal; Find in Folder; Add to Agent Chat. On test files it adds Run Tests (and Debug Tests for Go); inside a repository, Show History; on changed files, Show Diff and Rollback.
- This is the same context menu used by the terminal and the editor gutter (`openContextMenu`).
- Open tabs (including file history tabs) and breakpoints follow a rename. Tabs of deleted files are closed.

### Multiple folders in one window

You can attach more folders to the one open in a window, its workspace (like "Attach project" in IntelliJ):

- "Add Folder to Workspace…" (`⇧⌘O`, File menu, or `⌘O` / Recent Folders with `⌥↵` or `＋`).
- The tree then has one section per folder, each with "Remove from Workspace".
- `⌘P` and Search cover all folders (results are prefixed with the folder; Find in Folder narrows to one).
- The Commit panel shows the repository of the active tab's folder and has a switcher with the number of changes per folder.
- Update Repository (pull) asks which repository to update when the workspace has several (see [Git](#git-intellij-style)).
- New terminals and chats start in the active tab's folder (the `+` menu has a section per folder).
- Run configurations follow the active tab too: the ▶ selector in the title bar shows the configurations (`.flint/run.json` and detected ones) of the active tab's folder, with its name. Each folder remembers its own selection, and Run / Debug start in that project.
- "Fix with agent", `⌘L` and test results go to the chat of the folder the file belongs to.
- The command palette has "Add Folder to Workspace…" and "Remove <folder> from Workspace".
- LSP servers and the file watcher run per folder.
- The set of folders is restored after a restart, together with the session of the main folder.
- Terminals come back as new shells in their last directory. If Claude Code or Codex was running in one, it is started again on the same conversation (`claude --resume <id>`, or `claude --continue` / `codex resume --last` when the conversation's id is not known).

### Live agent changes

FSEvents with one recursive subscription per folder. The file tree refreshes and open files reload in place with a minimal diff. If you have unsaved changes, you get a warning.

### Markdown and image preview

- **Markdown**: an Editor / Split / Preview switch on `.md` files (`⇧⌘V`). Rendering happens in Go (goldmark, GFM: tables, task lists, strikethrough, autolinks), live while you type. In Split mode the preview follows the heading visible in the editor. Raw HTML and `javascript:` links are dropped. Relative links open files in the editor, external links open in the browser, and relative images load only from open folders.
- **Images** (`png jpg gif webp svg ico bmp`) open in a preview tab: fit to window, zoom with `⌘+` / `⌘-` / `⌘0` and `⌘`+scroll wheel, a checkerboard behind transparency, dimensions and file size. SVG can be switched to its source. An image you open yourself previews from anywhere, like a file in the editor (a screenshot an agent left in a temp folder). Limit: 25 MB per image.

### Search and replace

- `ripgrep --json`. Results stream in batches and are rendered virtually. Without `rg` a slower pure-Go fallback is used.
- **Workspace-wide replace** (`⇧⌘R` or ⇄ in the panel): a preview at every match (old text struck through, new text next to it), checkboxes per file and per line, and `$1` / `${name}` groups in regular expressions.
- The preview and the write use the same Go matcher, so exactly what you see is what gets written.
- On write every file is read again: files changed since the search, binary files, files that are too large and files with unsaved changes in the editor are skipped.
- Writes are atomic and preserve permissions and line endings. The last replace can be undone (*Undo*).

### Go to file (`⌘P`)

The file list comes from `rg --files` (respects `.gitignore`) and is kept in Go. Fuzzy matching also runs in Go; only the top 60 results are sent to the WebView. There is no up-front indexing.

### TODO list

Panel ☑ (palette: "TODO List"):

- Markers `TODO`, `FIXME`, `HACK`, `XXX`, `BUG` (whole words, upper case) across all workspace folders, using the same search as `⇧⌘F` (ripgrep, honoring `.gitignore`).
- Grouped by file, with the author from `TODO(who)`, and filters by marker and text. Click opens the file at the line.
- Refreshes after file changes (debounced), only while the panel is open.

### Language servers (LSP)

- `gopls`, `rust-analyzer`, `vtsls` / `typescript-language-server`, `basedpyright` / `pyright`. A server starts in the background on the first file of its language.
- Completion, hover, `⌘`+click / `⌘B` / `F12` go to definition, `⌥F7` / `⇧F12` Find Usages, live diagnostics (`⇧⌘M` problems list, `F8` next problem).
- **Navigation**: `⌥⌘B` Go to Implementation, `⇧⌘B` Go to Type Declaration, `⌘F12` *Go to Symbol in File…* (the file's outline with a filter; nesting is shown until you type) and `⌥⌘O` *Go to Symbol in Workspace…*, which asks the running language servers of the open folders (at most 200 results; a server starts when a file of its language is opened, so there is nothing to search before that).
- **Rename** (`⇧F6` or `F2`, "Rename Symbol…"): a small input at the symbol with its current name; `↵` asks the server for the edits (`textDocument/rename`, after `prepareRename` where the server has it) and applies them. Files open in an editor are changed in their buffer, as one undoable step each, and stay unsaved; files that aren't open are rewritten on disk by Go (atomically, keeping permissions and line endings), only inside an open folder with a running language server, never in `.git`, never through a symlink, never a file over 10 MB or one that isn't UTF-8. A note says how many edits went into how many files. Edits the server computed for an older version of an open file are refused, and so are changes that create, rename or delete files (Flint doesn't announce support for them).
- **Quick fixes and refactorings** (`⌥↵` or `⌘.`, "Show Quick Fixes and Refactorings…", and **Quick fix…** in a problem's tooltip): the server's code actions for the cursor or the selection (fixes, refactorings, organize imports and fix-all; actions that only open a web page or the server's own UI are not listed), the preferred fix first; quick fixes that extensions attach to their editor marks at the cursor are listed after them. Choosing one resolves it (`codeAction/resolve`), runs its command if it has one (`workspace/executeCommand`; the edits the server sends back with `workspace/applyEdit` are collected) and applies the result like a rename. The server gets back its own diagnostics for the range, unchanged, so fixes that depend on a diagnostic's code or data work.
- **Formatting**: `⌥⌘L` or `⇧⌥F` *Reformat File* (`textDocument/formatting` with the file's indentation: gofmt through gopls, rustfmt through rust-analyzer, …) and `⇧⌥O` *Organize Imports*, each one undoable step. `editor.formatOnSave` and `editor.organizeImportsOnSave` (Settings ▸ Editor, both off by default) run them before every save; a save never waits more than 3 seconds for the server and is never blocked by a missing formatter.
- **Parameter info**: after `(` or `,` (the server's own trigger characters) a tooltip shows the signature of the call with the current parameter highlighted and its documentation; it follows the cursor and closes with `Esc`. `⇧⌘Space` opens it by hand.
- On errors and warnings there is a *Fix with agent* button (and *Fix all N in file*, also `⌥⇧⌘L`): the chat receives the path, line:column, severity, source (for example gopls), message and the surrounding lines as an attachment.
- Server status and an install hint are shown in the status bar.

### Vim mode

- `editor.vimMode` (Settings ▸ Editor, or "Toggle Vim Mode" in the palette) turns on Vim key bindings in every editor, live, through [`@replit/codemirror-vim`](https://github.com/replit/codemirror-vim) loaded as a separate chunk only when the mode is on. The status bar shows `-- NORMAL --`, `-- INSERT --` or `-- VISUAL --`.
- `:w`, `:q`, `:wq` and `:x` save and close the file's tab; in diffs and other read-only views they only show a note.
- A focused Vim editor keeps `⌃` plus a letter, `[` or `]` (redo, half-page scrolls, visual block, and so on); Flint's own `⌃R` / `⌃D` still work outside editors, and `⌘` shortcuts work everywhere.

### AI in the editor

- **Edit with Agent** (`⌘I`, "Edit Selection with Agent…"): a prompt above the selection (or the cursor's line). The default agent runs headless with the file path, the selection and `inlineEdit.contextLines` lines around it (secrets redacted), and its answer replaces the selection as one edit (`⌘Z` undoes it), but only if that text hasn't changed meanwhile. `Esc` stops the agent. Claude Code runs with only `Read`, `Grep` and `Glob` and no MCP servers; Codex with `--sandbox read-only`; a custom agent only in a trusted folder. Files that hold secrets (`.env*`, keys, `credentials`, kubeconfig, …) are refused.
- **Inline completions** (off by default): ghost text from a fill-in-the-middle model, Ollama (`/api/generate`) or an OpenAI-compatible server (`/v1/completions`), requested after a typing pause. `Tab` accepts, `Esc` or any other edit dismisses, and each new request cancels the previous one. Plain `http` is allowed only for `localhost`; for a remote endpoint secrets in the context are redacted, secret files are never sent, and the API key lives in the Keychain per endpoint origin. The status bar shows ✦ while on and ⚠ with the error (for example "Ollama is not running").

### Scratchpads

Persistent SQL consoles and notes (MD/TXT) with autosave. `⌘↵` runs the query under the cursor or the selection. Results go to a virtualized table (up to 200k rows) with export to TSV/JSON.

## AI agents

### Agent chat

- Native drivers, **no npm**: Claude Code (`claude -p` in `stream-json` mode with `--permission-prompt-tool stdio`) and Codex (`codex app-server`).
- Any other agent with an [Agent Client Protocol](https://agentclientprotocol.com) mode, added in Settings ▸ Agents ▸ Custom agents (ACP) with no code: Flint starts its command (for example `gemini --experimental-acp` or `opencode acp`) and speaks ACP over stdio (`internal/acp`, `agentsession/acpdriver`). See [Custom agents (ACP)](#custom-agents-acp).
- Your own agents: a Markdown file with an optional engine and model (or model tier) and standing instructions, usable wherever an agent name is. See [Defined agents](#defined-agents).
- A shared panel in the right dock (`+` → claude / codex / a custom agent): streamed response, tool calls with a mini diff, the plan, and the list of changed files.
- Edits and reads go through without asking (the "auto: edits" policy), except outside the chat's folder and inside the protected folders (`.git`, `.claude`, `.codex`, `.vscode`, `.idea` and `.flint`, which holds the workflows, run configurations, agents, roles and prompts Flint runs), which ask; commands ask for permission.
- `⌘L` attaches the selection or the current file to the conversation.
- "Send to agent" (LSP problems, terminal output) uses the shared `askAgent` (`frontend/src/lib/askAgent.ts`): it picks the active or most recently used chat of the folder the content belongs to (the file's folder, or the active tab's folder when there is no file). If there is none, it opens a new chat in that project with the preferred agent. The content goes into the draft so you can add to it; `⌥`-click sends it immediately.
- Prompt library (`internal/prompts`, `PromptsAPI`, `components/agent/PromptPicker.tsx`): typing `/` in any chat lists Markdown prompts from `.flint/prompts` (repository), the config dir's `prompts/` (personal) and the built-in `/review`, `/test`, `/explain`, `/fix` (`prompts.builtins`), project over personal over built-in. Optional front matter: `description`, `agent`, `args`. Choosing one fills the draft with `{{selection}}` and `{{problems}}` (redacted; no selection from a credentials file), `{{file}}`, `{{diff}}` (bounded, redacted, credentials files such as `.env` left out and only named; `redact.SecretFile`), `{{branch}}` and the args filled in (one pass); nothing is sent automatically. Text that matches no prompt, or anything sent after `Esc`, reaches the agent unchanged (`/compact`). "Run Prompt…" and "New Prompt…" in the palette. Files are read when the list opens (no watcher, no polling); only regular files ≤ 64 KB that stay inside the folder (and the project) after resolving links. In Restricted Mode project prompts are marked "untrusted repo" and can't replace a built-in or personal one.
- The chat header shows usage: cumulative input/output tokens, cost in USD when the agent reports it (codex usually does not), and a context fill bar (for example "42% context"), with details in a tooltip. The status bar shows the total for the folder (with several folders, for the whole workspace, broken down in the tooltip). Usage is part of the saved session.

### Usage and budgets

- Usage is recorded in Go as it arrives: every `usage` event of a chat is one turn, added to a daily row per folder (a task's chats count for the repository's main checkout), agent, model, agent task and chat in `usage.json` (`internal/usage`, `usage_state.go`). Tokens in/out, cache read/write tokens when reported (Claude Code, Codex), the cost only when the agent reports it. A turn Claude Code reports per model is split by model. A resumed conversation counts only its new turns (Codex's first total after `thread/resume` and Claude's first `total_cost_usd` after `--resume` cover the history). Writes are batched (about 2 s, and on quit) and atomic; the file is bounded by `usage.retentionDays` (default 90) and row/chat caps. A file that can't be decoded is moved to `usage.json.bad-<time>`; one that can't be read or comes from a newer Flint is never overwritten. Custom ACP agents send no usage and aren't recorded.
- No invented prices: tokens without a reported cost stay tokens, unless `usage.prices` gives the model a price ($/Mtok in/out, optional cached input); those costs are kept apart and always labelled as estimates, and cached input without a cached price is left out (and said so) rather than priced as fresh input.
- The Usage panel (∑, `UsageAPI`) shows today / 7 / 30-day totals, a per-day SVG bar chart (7 or 30 days), breakdowns by folder, agent task, agent and model (click a folder or task to filter), top chats, and a CSV export of the daily rows (native save dialog; a download in the browser build). It reloads on `usage:changed`, never polls.
- Budgets: daily (USD and/or tokens, all chats) and per agent task; token budgets leave out cache reads unless `usage.countCacheReads`. When a turn reaches one, `usage:alert` fires once per threshold per day or task (remembered in `usage.json`, so not again after a restart): a warning under the chat header, a toast, or a background notification through `AlertsAPI`. With `usage.pauseOverBudget`, `AgentChatAPI.Prompt` refuses new turns until **Continue anyway** in the warning, which lasts for another budget's worth at that limit.
- Nothing is sent anywhere; see [Files and data](../site/reference/files-and-data.md).

### Custom agents (ACP)

- Each entry in `customAgents` (settings.json) is an agent: an id (lowercase, not `claude` or `codex`), an optional name, a command (a name on the login PATH or an absolute path) and the arguments that start its ACP mode. Settings offers Gemini CLI (`gemini --experimental-acp`) and OpenCode (`opencode acp`) as one-click fill-ins; you install and log in to the CLI yourself.
- **Check** first asks, in a native dialog that shows the exact command line, before it runs a command line for the first time in a session. It starts the agent in an empty temporary folder, runs the ACP `initialize` handshake (25 s timeout) and shows its name and version, or the error with the end of what the agent printed. No session is opened.
- A custom agent appears in the agent menus, the default-agent pickers and "Ask the agent" once its command is found. Saving settings registers the agents again; open chats keep the agent process they started with.
- It starts only in a trusted folder (see [Restricted Mode](#restricted-mode-workspace-trust)). Its permission requests go through the same approval policy as the native agents. Flint offers it file reads and writes (ACP `fs/*`) only inside the chat's folder, never into `.git`, and no terminal; the agent runs in its own process group, which is killed when the chat closes and when Flint quits.
- There is no environment setting: `settings.json` is plain text, so API keys don't belong there. Log in with the agent's own command (`gemini`, `opencode auth login`) before using it.
- Custom agents can't be resumed after a restart; a restored chat continues in a new conversation and says so.

### Defined agents

- A defined agent is a Markdown file in the prompt-file format (`internal/agentdefs`, [design](design/agent-definitions.md)): optional `description` (200 characters), `engine` (`claude` or `codex`) and `model` (a model tier, `fast`, `balanced` or `strong`, with or without an engine; any other value is a model name, only with an engine, checked by `agent.CheckModel`), then the standing instructions (required, 16,000 characters). The name is the file name without `.md`: lowercase letters, digits and dashes, starting with a letter, at most 32 characters; `claude`, `codex` and a custom agent's id are refused. At most 64 KiB per file and 50 per folder; unknown keys are ignored. A file that breaks a rule is skipped and reported as a problem (path and reason).
- Personal definitions live in `agents/` of the config directory; repository ones in `.flint/agents/` of each workspace root, **only when the root is trusted** (an untrusted root's files are only counted and reported as ignored). A personal definition wins over a project one with the same name, the first root over later ones; symbolic links that leave a root are refused.
- A defined agent is an agent wherever a name is: chat menus, New Agent Task and Compare agents, `defaultAgent`, `agentReview.agent`, the prompt library's `agent` key, `start_agent` and the usage breakdown. Settings accept any name of the custom-agent-id form there; a name that is not available falls back as a missing custom agent does.
- Without `engine`, the agent runs on `defaultAgent` when that is an installed native agent, else the first installed one (`agentdefs.ResolveEngine`; a defined or custom default is never followed). The engine is resolved when a conversation starts and recorded as `SessionInfo.engine`; the chat saves it and `AgentChatAPI.Resume` takes it back, so a conversation resumes on the engine it started on. A defined agent is listed only when its engine is installed.
- The instructions are standing instructions for the whole conversation, at start and at resume: `--append-system-prompt` for Claude Code, `developerInstructions` for Codex, never through a shell. Headless runs use the engine and the model; Review Changes with Agent also passes the instructions (one argument: `--append-system-prompt=…`, or Codex's `-c developer_instructions=…` as an escaped TOML string), so a reviewer set as the review agent reviews by its rules. Commit messages and Edit with Agent leave them out (their answer has a fixed form); the conflict terminal runs the plain engine (`agentView.native`).
- Files are read again when agents are listed and before a chat starts or resumes (no watcher), once per call: a change applies to the next conversation, without a restart; running chats keep their driver. A chat starts on the definition its own call read, whatever another call reads meanwhile (`Manager.StartWith`). A chat whose definition is gone fails to resume with a message naming it.
- A role limited to `claude` or `codex` (`start_agent`'s roles, a prompt's `agent` key) also fits a defined agent that runs on that engine; one that names a defined agent fits only that agent.
- Model tiers: `agents.<claude|codex>.tiers` maps `fast`, `balanced` and `strong` to a model of that engine (each checked by `agent.CheckModel`; an unknown tier or a bad model is refused on save and dropped on load). Claude Code defaults to `haiku`, `sonnet` and `opus`; Codex has no defaults. A missing tier uses the default, `""` none; a tier without a model leaves the engine's `model` in place. The tier is resolved from the settings of the moment a conversation starts or resumes, on its engine (`definedModel`), and the same way for headless runs (review, commit message, inline edit). `AgentDefsAPI.List` returns `model` as written and `resolvedModel`, its meaning on the resolved engine now (`""` when none); Settings and the pickers show `strong (opus)`, or `strong` when unmapped. Settings ▸ Agents has a field per tier in each engine's block, with the default as placeholder.
- A definition cannot add arguments, tools, permissions or environment; a tier only resolves to a model from the user's own settings or the built-in defaults. Not in version 1: custom ACP agents as engines, per-agent permissions, tools, budgets or scope, the background session host. A definition cannot describe steps between agents (that is what [Workflows](#workflows) are for).
- Settings ▸ Agents lists the definitions (name, engine, model, source, description), the problems and the folders ignored in Restricted Mode, with **New Agent…** (a template in the personal folder or a trusted root's `.flint/agents`, never overwriting) and **Open**; the command palette has **New Agent Definition…** (`AgentDefsAPI`). Pickers show "name · engine" or "name · default (engine)".

### Agent tasks (parallel agents in worktrees)

- "New Agent Task…" (palette, or `＋` in the Agent Tasks panel ⑂): a description, an agent (default from settings; Claude Code, Codex, a custom agent or a defined agent; several with "Compare agents") and a base branch (default: current). Flint creates a branch (`agentTasks.branchPrefix` + a slug of the first line, made unique) and a worktree (`agentTasks.worktreeDir`, default `<repo>.worktrees/<branch>` like the branch widget), attaches it to the window, starts a chat there and sends the description as the first message (`TaskAPI`, `internal/agenttask`).
- The panel lists the tasks of the open repositories with their state (queued / working / waiting for approval / idle / finished / failed), derived in Go from the chats' agent session events (`agenttask.Tracker`, bound when a chat starts or resumes in the worktree; no polling), the branch, commits ahead of base, and changed files with +/- against the merge base (committed, uncommitted and new files), refreshed on file-watcher and git events.
- Actions: Open (folder + chat), Show diff (per-file side-by-side diff against the merge base), ✦ Ask agent on a failed task (error in the chat draft), Merge (in the checkout where base is checked out; refused while the task or that checkout is dirty; conflicts are found with `git merge-tree` without touching anything, and Flint offers to merge base into the task and hand the conflicts to the agent in a terminal), Create PR (push of `refs/heads/<task>` + `POST /repos/…/pulls` after a native confirmation; a branch pushed to a fork becomes `owner:branch`), Remove (stops the chats, deletes the worktree; uncommitted work and unmerged branches only after confirmation).
- Compare agents: the form's "Compare agents" sends the same description to several agents and/or several attempts per agent (at most `agenttask.MaxGroup` = 6 tasks). `TaskAPI.CreateGroup` makes one task per choice from the same base commit, each with its own branch (the slug plus the agent's id, made unique: `agent/add-retry-claude`, `agent/add-retry-codex`, `agent/add-retry-codex-2`) and worktree, all or nothing, and links them by a group id stored with each task (`group` in `state.json`; files without it load as tasks on their own). The panel shows a group together under its title with each task's state, agent, +/-, commits ahead and the tokens and cost of its chats (`usage.Store.TaskTotals`, also shown for single tasks).
- **Compare** on a group opens the comparison (`TaskAPI.Compare`, `CompareFile`, `DiffBetween`; `internal/agenttask/compare.go`): the union of files changed by any task with each task's +/- per file, and for the selected file every task's diff against its merge base side by side as unified diff lines computed in Go (work tree included, like Show diff; **Open diff** opens the usual side-by-side diff tab), plus a direct diff of the file between two tasks. Files are read through `os.Root`, so a path or a symlink can't leave the worktree; binary files and files over 1 MiB are named, not shown.
- **Keep: Merge** / **Keep: PR** on a task of a group are Merge and Create PR for that task; after they succeed Flint offers to remove the other tasks of the group. Each removal is the ordinary Remove: uncommitted work and unmerged branches go only after their own confirmation.
- **Origins**: a task a feature made carries `origin` in `state.json` (the feature's opaque note of what the task is for, at most 8 KiB, set only by Go; files without it load as tasks without one). When Go starts the chat of such a task (the queue, **Start now**, a feature's create, a joint group's lead), the features are asked for context to put before the description (`feature.Instance.TaskContext`); the stored description, the panel and the title stay the item's own text. **Start now** on such a task is started by Go, not the window (`TaskView.flintStarts`, as for a joint group). Tasks made with New Agent Task have none and are started as before.
- **Joint groups** (one agent across 2 to 10 repositories, made by a project item with `together: true`; described under Projects): the tasks carry the same `joint` id and `lead` on the first one in `state.json` (files without them load as tasks on their own); the panel shows them together with the lead marked, they share one chat and so one state, and Merge, Create PR, Show diff and Remove work per task. The group holds one queue slot and is queued and started as a unit (`Start now` on any task); removing a task whose chat is shared stops that chat for the whole group after the question says so (`RemoveInfo.StopsJointChat`, `JointTasks`).
- Queue: at most `agentTasks.maxParallel` tasks (default 3, 0 = no limit) work at the same time, counted in Go over the window: tasks with a turn running (working or waiting for approval) plus tasks whose chat is being started. A task created beyond that is **queued** (`queued` in `state.json`): its branch and worktree are created at once (so a group shares one base commit and a queued task can be inspected and removed), but no chat starts and the description is not sent. When a task settles (finished, failed, cancelled, chat closed: the same `agenttask.Tracker` change that updates the panel, no polling), is removed, or the limit is raised, the oldest queued task whose repository is open in the window gets the slot: Go starts its chat itself (`App.openChat` in the task's worktree, the stored description with secrets redacted as the first prompt, shown as "from Flint (task)") and the window adopts it, showing the task's folder first; the chat is started once, even when the window is reloaded meanwhile. **Start now** on a queued task overrides the limit. A queued task never starts by itself in an untrusted (Restricted Mode) worktree, and neither the queue nor Start now starts one while `usage.pauseOverBudget` holds a spent budget (**Continue anyway** lets the queue move). After a restart queued tasks stay queued until their repository is open in a window and a slot is free. The limit is per window (each window is its own process).
- Tasks are kept per repository (keyed by the common git dir) in `state.json` with their last settled state and the agent's session id of their latest own chat (not chats their agent started). A turn is saved as **interrupted** from the moment it starts (a crash or a kill leaves no chance to save later); its end replaces that with finished or failed, a cancel clears it, and a chat closed mid-turn keeps it, so a turn cut off by quitting Flint shows as interrupted instead of idle. **Open** on a task with no chat open reopens that session dormant (the agent resumes the conversation with the next message, `AgentChatAPI.Resume`) instead of starting an empty chat; **Ask agent** is offered for interrupted tasks as for failed ones, in that resumed conversation; a task whose worktree vanished is shown as stale and can be removed (only its own entry under `.git/worktrees` goes; other missing worktrees are left alone). A task's worktree is trusted when the checkout it started from is trusted; a task from an untrusted checkout may not put its worktree inside a trusted folder (trust is by path), and no task worktree may lie inside the checkout. Worktrees made by hand from the branch widget don't inherit trust. Branches are always named by full ref (`refs/heads/…`), so a same-named tag can't stand in for one; the base must be a plain local branch name.

### Projects (work items above repositories)

A project is a folder of work items, described below. The folders open in the window are workspace folders, and the one the user works in is the active folder.

- A project is a folder with `flint-project.json` (`name`, at most 80 characters, default the folder's name; `repositories`, at most 50, each `name` (lowercase letters, digits and dashes, at most 40, unique) and a git remote `url`) and `items/*.md`, one level, at most 500 files of 64 KiB. Unknown JSON fields are ignored; a project without repositories is valid. An item is a prompt-file-format Markdown file (`prompts.FrontMatter`): id = the file name without `.md` (`prompts.ValidName`), `title` (required, 120 characters), `status` (`todo` default, `doing`, `review`, `done`), `priority` (`low`, `normal` default, `high`), `agent` (any agent name; empty = the default agent), `repos` (comma-separated names from the file; empty = the window's active folder), `after` (comma-separated ids of items of the same project, at most `MaxAfter` = 20, none twice; a value that is not an id makes the file a problem) and `together` (`true` or `false`, default `false`; `true` needs 2 to `agenttask.MaxJoint` = 10 repositories in `repos`, else the file is a problem: "together: true needs two or more repositories in repos …"), then the body. Title and body together are at most `agenttask.MaxPrompt` = 8,000 bytes (counted in bytes, as New Agent Task counts a description), Delegate's note about several repositories included (an item with `together: true` has no note). Title and body (and the project's name, `PROJECT.md` and the planning goal) may not contain control characters other than tab and newline (U+0085 NEL among them: "a control character (U+XXXX)"), the line and paragraph separators U+2028 and U+2029 ("a line or paragraph separator (U+XXXX)": a reader may break the line there while the panel shows one, so a title could imitate the context block's delimiter), Unicode tags (U+E0000–U+E007F), bidirectional controls (U+202A–U+202E, U+2066–U+2069), U+200B, U+2060 or U+FEFF ("contains invisible characters (U+XXXX)"); zero-width joiner and non-joiner are allowed. A file that breaks a rule is a problem (file and reason), not an item; an unavailable agent keeps the item and adds a problem. Items sort by status (doing, review, todo, done), priority, title. Files resolve inside the project folder: a symbolic link that leaves it is refused. Code: `internal/features/projects` (`format.go`, `load.go`), design: [design/projects.md](design/projects.md), guide: [site/guides/projects.md](../site/guides/projects.md).
- Which projects Flint knows: the folders opened with **Open Project…** or made with **New Project…** (`flint-project.json` and an empty `items/`, never overwriting) kept in `state.json` (`projects`, most recent first, at most 20, forgotten on Close), plus the workspace roots that hold `flint-project.json` at their top (not closable). A project is known by its resolved path; the methods that take a project folder (everything but Open and New) refuse one Flint doesn't know. Closing one also drops the links of its items to agent tasks. The links of an item whose file is missing for a moment are kept (they go on Close or when pruned); renaming an item's file loses them. `ProjectInfo`/`Project` carry `trusted` (the project's folder, `Host.Trusted`).
- **Project context**: `PROJECT.md` at the top of the project folder (optional, plain Markdown: what the project is for, how its repositories fit together, conventions, definition of done) is read inside the folder (no symlink escape), at most 64 KiB, UTF-8, at most `MaxContextChars` = 16,000 characters, with the item's character rules (a leading byte order mark is dropped); a file that breaks one is a problem ("PROJECT.md: … (agents don't get the file until it is fixed)") and is not sent, and Delegate still starts and warns "the agents got no project context from PROJECT.md: …". Every chat of an item's agent task starts with a context block composed in Go when the chat starts (`taskContext`, through `feature.Instance.TaskContext` and the task's origin, so a queued task or a waiting start gets the state at its start): between "===== Project context (from Flint) =====" and "===== Your task =====", the project's name and folder and `PROJECT.md`, the item (id, title, status, which is always `doing` for the item being started, priority, file), what it depends on (title and status; for done ones the branches and pull requests of their tasks known on this machine, per repository), the other items in `doing` or `review` (title, agent, repositories; at most 20, saying how many more), the repositories with their URLs and where this agent works (a joint group: "after your task Flint lists which folder is which", as `jointPrompt` does), and `get_project` when Flint's MCP server is offered. A line inside the block that starts with `=====` (from `PROJECT.md` or any other text) gets "> " in front of it (`fenceSafe`), so nothing can close or reopen the block. For a project whose folder is not trusted at the chat's start, or was not when the Delegate was confirmed, the block holds only what the confirmation showed (`restrictedContext`): the first `maxConfirmContext` = 1,000 characters of `PROJECT.md` exactly as shown, only while the file still starts with them (their hash is in the task's origin, with a note when the rest was left out), the item's id, and its title and repositories as the origin kept them at Delegate; no project name, other item, dependency, URL or `get_project`. At most 24 KiB: the items in progress, the dependencies' branches, the repositories the item doesn't name and then the end of `PROJECT.md` are cut, in that order, saying so. It does not count against the item's 8,000 bytes. **Add Project Context…** (`API.AddContext`) writes `PROJECT.md` from a template (headings What this project is for, Repositories with the project's names, Conventions, Definition of done), never overwriting and never following a link, refused for an untrusted or unknown project; the UI opens it.
- The **Projects** sidebar panel: **＋** (New Item…: a title; the id is `agenttask.Slug` of it, `-2`… when taken; written from a template, never overwriting, and opened), refresh, and a `⋯` menu with **Open Project…**, **New Project…**, **Show Board** and **Close Project** (disabled for a workspace project); the project picker; a Restricted Mode note with **Trust Folder…** for a project whose folder is not trusted; a **Context** line (`PROJECT.md` with **Open**, "not sent" when it has a problem, or "none" with **Add Project Context…**; the board's header has the same); a **Repositories** group (each repository with its URL and checkout or "no checkout on this computer", markers no checkout / problem / located / not in workspace / Restricted Mode, **Locate…**, **Add to Workspace**, **Trust Folder…**; collapsed when every repository can be used); and the items grouped Doing, Review, To do, Done (Done collapsed; group headers are focusable buttons operated with Enter or Space). A row shows title, priority, agent, repositories and the states of its agent tasks; actions are **Delegate**, **Open** (the file), **Status ⌄** and **Open** on an agent task. Problems are listed under the items, each with **Ask the agent**. Delegate first walks through what is missing (Locate… after a confirmation naming the repository and URL, adding the folder, trusting it; a trust confirmation names the folder and says trust is for the whole folder from now on) and stops with the reason when a step makes no progress (`delegateStep`). The **Board** tab ("Project: <name>", restored with the session) has columns To do, Doing, Review, Done; a card can be dragged to another column. Commands, under "Projects" in the palette: Open Project…, New Project…, New Project Item…, Plan with Agent…, Show Project Board. The panel reads again when shown, on refresh, after Flint's own writes, when agent tasks change and when files change in a project inside a workspace root (`projects:changed`); a folder outside the workspace is not watched.
- Repositories and checkouts: a declared repository's checkout is a trusted workspace root whose repository has a remote (any remote) with the same URL, else the folder chosen with **Locate…** when trusted, else an untrusted workspace root with that remote (any folder can claim any URL, so an untrusted one never hides a trusted checkout), else the located folder; a repository nested inside an open folder is not found automatically (Locate… it). Located folders are kept in `state.json` `projectCheckouts` (per normalized URL, at most 200, never in the project). URLs compare by `RepoKey`: scheme, user, port, a trailing `.git` and slashes are dropped and the host is lower-cased (`git@github.com:acme/api.git`, `ssh://git@github.com:22/acme/api` and `https://github.com/acme/api/` are one repository); the path keeps its case; `file://` and absolute paths compare as cleaned paths; at most 1,000 characters, no spaces, control characters or `.`/`..` segments. **Locate…** accepts only a folder whose repository has a remote with that URL, and never an agent task's worktree; a located folder that has gone or no longer matches is reported as a problem of the repository. A located folder outside the workspace is attached to it by the UI before Delegate. A repository with no checkout can be cloned instead: see **Clone…** below.
- **Delegate** (`projects.API.Delegate`): first works out what the item waits for (below): an item that waits answers `NotReady` with `WaitingFor` and starts nothing, one whose `after` has a problem is refused ("<items/x.md> can't start: after: …: fix the item's after line"). Then resolves the agent (the item's, else the default; it must be available now), then every repository to a checkout that is in the workspace and trusted, and says in one message what is missing (no checkout, unusable located folder, not in the workspace, Restricted Mode). An item without `repos` uses the active folder the UI passes, which must be an open, trusted workspace folder. It then creates one agent task per repository through `createTasks` (an item with `together: true` and 2 or more repositories makes one joint group through `Host.CreateJointAgentTasks` instead, below) (the code of New Agent Task: branch from the checkout's current branch, worktree, queue, limits, trust), all or nothing (its tasks are held from the queue, `taskQueue.held`, until it succeeded or rolled back, so the queue never starts a task a rollback removes and their slots don't expire meanwhile; a detached HEAD is reported as "<folder> is on a detached HEAD: check out a branch there, then Delegate again"), and starts the chats of the tasks that got a slot (`startTaskChat`, as for a task that leaves the queue); the others are queued. The description is the title and body, with several repositories also a sentence naming the item's repositories and the one the task works in (refused when that makes it longer than 8,000 bytes). For an item of a project whose folder is not trusted, Go first asks in a native confirmation (`Host.Confirm`) showing the agent, the target folders and the description (its first 1,000 characters, saying when it is cut) and, when there is one, that `PROJECT.md` is sent too, with its first 1,000 characters; No creates nothing. Such a project's agents get `PROJECT.md` only while it hashes to what was shown (kept in the task's origin), their own item and the repositories' names, never other items or URLs. It then remembers the tasks (`state.json` `projectTasks`: per project and item at most 100 links; removed ones are dropped first, and Delegate is refused when none can go) and sets `doing`; when the status can't be written, the tasks stay and the result carries a warning. Delegating again adds tasks. One delegate of an item runs at a time, whoever asks (`API.starting`); a second one fails with "the item is being started already: wait a moment".
- Status is written to the item's file: only the value of the `status` line changes (a line is added before the closing `---` when there is none), the rest stays byte for byte with the file's line endings, and the new text must parse to the same fields. A file with two `status` lines, no closing `---`, a line that is not `key: value`, or one that changed between reading and writing (compared just before the new file, already written next to it, replaces it) is refused with the reason. The user can set any status; automatic changes are `doing` → `review` when every counted task finished, `review` → `done` when every counted task is merged or was removed after its pull request was created (`NextStatus`; both in one step is possible), and a failed task keeps the item in `doing`, marked. An automatic change happens only when something about the item's tasks changed since the last look, so an item the user moved stays where they put it until its tasks change; a change that can't be written is tried again next time. A task removed with neither merge nor pull request no longer counts; with none left nothing moves. Links keep the last state, pull request and merged flag, so removal doesn't lose them. Changes are made on `TasksChanged` (with every `tasks:changed`, and at start), whenever the panel loads the project, and nothing polls.
- The link between items and agent tasks and the waiting starts are local state; statuses, items and `flint-project.json` are files a team shares through git. Agent tasks, chats, worktrees, waiting starts, located and cloned folders and the list of projects stay on one machine.
- `get_project` (read-only, on Flint's MCP server while the feature and the server are on, and not in untrusted folders): optional `status` and `project` (name) arguments, unknown arguments refused. For a chat that is an item's agent task (`mcpserver.CallerFrom` → `Host.TaskOrigin`) it returns that project first and in full ("You are working on the item …", the item marked and listed first), the other projects by name only; for another chat the projects with a repository whose URL is a remote of the chat's folder come first. The answer lists every known project whose folder is trusted with its repositories and items (id, title, status, priority, agent, repositories with "(together: one agent works in all of them)" for a joint item, `after` with "(ready)", "(not ready: waits for …)" or "(never ready: <problem>)", the workflow runs of its tasks as they are now, "runs: bug-fix · waiting for the user's approval (run <id>, api)", the newest 5 per item, text cut at 2,000 bytes), bounded to 60 KB with headings and repository lists counted, with a count of what was left out, and reports a project it cannot read; projects in untrusted folders are left out with a count and the reason. It is not in `agentsession.MCPReadTools`, so Claude Code asks for each call like it does for terminal output.
- Delegate, and a waiting start the user allowed by name (below), are the only things that start an agent besides an agent's `delegate_project_item` call the user approved (below): opening a project reads files, and agents have no tool that sets a status or changes an item. An agent can delegate a ready item only when "Delegate project items" is on, only with the user's yes to that one call, never an item that waits for others, never from a project whose folder is untrusted, and never from inside handed-out work (an agent task's chat or worktree, or a workflow step). It is refused for a checkout in Restricted Mode. The feature is optional (`features.enabled.projects`, Settings ▸ Extensions ▸ Built-in); switched off, `get_project`, `add_project_item` and the starter are not started.
- **Plan with Agent…** (`API.PlanPrompt(folder, goal)`; panel and command palette): the goal is 1 to `MaxGoal` = 2,000 characters with the item's character rules ("say what the goal is", "the goal is longer than 2000 characters", "the goal contains a control or invisible character (U+XXXX)"); a project whose folder is not trusted is refused. It returns the prompt for a chat's draft (the user sends it; nothing is sent for them) and `toolOn` (Flint's MCP server is on and `mcpServer.actions.projects` is). The prompt (`planText`, next to the parser so the format is described once) gives the goal, the project's `PROJECT.md` (at most 8,000 characters, saying when it is cut, so the planner splits the goal in the project's terms), the project's name, folder and repositories, the item format with its limits including `after` and `together`, the available agents (at most 30) and the default one, and tells the agent to read the project with `get_project`, add items with `add_project_item` in an order where an item only waits for existing items, correct refused calls, tell the user to switch on "Add project items" if the tool is missing, and list what it added.
- **`add_project_item`** (`api.addTool`, `mcpserver.Tool.Acts`; offered only while `mcpServer.actions.projects` is on; Settings ▸ Agent Context ▸ Actions ▸ "Add project items"): arguments `project` (folder or name; a name only among projects whose folder is trusted), `title`, `text` (required, may be empty), `priority`, `agent`, `repos`, `after`, `together`; unknown arguments are refused. `Plan` checks the call before the user is asked (the same code as **New Item…** and the parser: id from the title, never overwriting, status always `todo`, every limit and character rule, an agent that is available here, `after` naming existing items without a cycle, a project whose folder is trusted) and returns the summary the user approves (name, folder, title, priority, agent, repositories, together, after, file name, the first 600 characters of the text); the write after the yes checks it all again. One chat adds at most 50 items (counted by `mcpserver.CallerFrom`), the project's 500-item limit holds.
- **`delegate_project_item`** (`delegatetool.go`, `mcpserver.Tool.Acts`; offered only while the MCP server and `mcpServer.actions.delegate` are on; Settings ▸ Agent Context ▸ Actions ▸ "Delegate project items", off by default and separate from "Add project items"): arguments `item` (required) and `project` (folder or name; default: the one project the chat's folder is in that has the item); unknown arguments are refused. It runs the **same function as the Delegate click** (`delegate`, whose checks are `prepare`): the item must be ready (an item that waits is refused with what it waits for, and an agent cannot ask to start it when ready), its agent available, every repository a trusted checkout in the workspace (an item without repositories runs in the chat's folder), the workflow it names able to run (`Host.CheckTaskWorkflow`), and script steps without a sandbox refused until the user ran such a workflow in that checkout. A project whose folder is not trusted is refused outright (no confirmation is offered to an agent). The chat must be in a trusted workspace folder that is **in** the project (the project's folder is the chat's folder or inside it, or the chat's checkout is one of the project's repositories) and must not be handed-out work (an agent task's chat, its worktree, a workflow step). `Plan` returns the summary the user approves: the project, the item's id and title, its agent or workflow, each repository with the folder its task is made from, whether one agent works in all of them, and the first 600 characters of the item's text; the run after the yes checks everything again. One chat delegates at most 10 items (a refused call is not counted, and a chat at its limit is never forgotten). The tasks' origin (`origin.By`) and Flint's log say "an agent in <folder> (chat <id>)" delegated them; a workflow's runs get `Origin: "agent"` and the log line "Run started for a project item, delegated by an agent in <folder> (chat <id>), approved by you".
- **Dependencies**: `Dependencies(items)` gives each item `WaitingFor` (items of `after` that are not `done`, in order) and `Problem` ("after: the item names itself", "after: no item x in this project (or its file has a problem)", "after: a cycle: a → b → a"). An item is ready when it has no problem and waits for nothing. An item with a problem is shown, listed under the problems and never ready; an item that waits for an item on a cycle is not a problem but is not ready until that one is done.
- **Waiting starts** (`StartWhenReady`, `CancelStart`; `state.json` `projectWaiting`, at most 100 per project, forgotten with Close Project): Delegate's `NotReady` answer is followed by the user's yes, which records the item (with a hash of its file, `Waiting.Hash`, and the active folder for an item without repositories, which must be an open workspace folder); an item that is ready by then starts at once, and an item that is `done` or has an `after` problem is refused. The `starter` goroutine is woken after the watcher's reconcile, on `SetStatus`, on a load of a project with waiting starts, on `RootsChanged` and by `StartWhenReady`; nothing polls. It delegates a ready item through the same `delegate` function as a click (every check, the untrusted-project confirmation which then names the item and why it starts now, the task limit), once; a failed start keeps the item waiting with the reason (`Waiting.Reason`) and emits `projects:auto-start`, and is tried again only when a fingerprint of what the checks read (item file, `flint-project.json`, agents, checkouts, active folder, trust) changed. An item that is `done` by then is not started and its entry is dropped; declining the confirmation leaves it waiting. An item whose file is not exactly the hashed one any more (its text, agent or repositories changed, or another item took its id) is not started: it keeps waiting with "the item changed since you asked: Delegate it again or cancel the start" (`Waiting.Changed`), reported once and not tried again until the user delegates it, asks Start When Ready again (a new hash) or cancels; Flint's own rewrite of its status line keeps the hash in step. While its file is missing it waits; New Item… and `add_project_item` never give a new item the id of a waiting start. A dependency's status changed by anyone (a teammate's pull, an agent editing the project's files) still starts the item: that is what the user asked for.
- **Clone…** (`API.Clone(folder, repo, parent)`, `CancelClone`; `internal/git/clone.go`): the UI picks `parent`; the checkout is `parent/<last part of the URL's path without .git>`, which must not exist or be an empty folder (not a link), 100 characters at most, letters, digits, `.`, `-`, `_`, not starting with `.` or `-`, not a reserved Windows name. `CloneSource` accepts only `https://host/path` (no user), `ssh://[user@]host[:port]/path` and scp-like `[user@]host:path` (at most 1,000 characters, ASCII without spaces, a host of 2 or more plain characters and a plain user, no password, query, fragment, `::`, `\`, `[`, `]`, `.` or `..` segment, nothing that starts with `-`); others fail with "<url> can't be cloned: only https://, ssh:// and user@host:path URLs can be cloned (…)" or the specific reason. `https://` URLs with a user name are refused too ("the https URL holds a user name (it may be a token): use a credential helper instead"); `ssh://user@host/…` and `user@host:path` keep theirs. Trust covers subfolders, so a clone into a trusted `parent` would be trusted at once: for a project whose folder is not trusted, Clone refuses such a `parent` ("choose a folder that is not inside a trusted folder: a clone there would be trusted at once, …"), checked before and again after the confirmation; for a trusted project the native confirmation says "The new folder WILL BE TRUSTED at once, because it is inside the trusted folder <parent>" instead of "in Restricted Mode until you trust it". The confirmation shows the URL and the folder (and, for an untrusted project, a note to check the URL). git runs with `protocol.allow=never` and only the URL's transport allowed (`ext` and `fd` never), the URL after `--`, `--no-recurse-submodules`, `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `GIT_TERMINAL_PROMPT=0` and `SSH_ASKPASS_REQUIRE=never` (credentials come from the user's helper or agent). One clone per project at a time; cancellable (`CancelClone`, Close Project, Flint quitting) and stopped after 30 minutes; made in a `.flint-clone-*` folder in `parent` and renamed into place only when it worked, removed otherwise. Progress is `projects:clone-progress` (at most every 250 ms, lines cut at 300 characters), the end `projects:clone-done`. The folder is remembered like a located one (`projectCheckouts`) and is not added to the workspace by Go (the UI does that for Delegate); the returned `RepositoryView.trusted` and the UI's message say whether it is trusted.
- **One agent across repositories** (`together: true`; `tasks_joint.go`, `internal/agenttask/joint.go`, `Host.CreateJointAgentTasks`): Delegate makes its usual checks and then one **joint group** of 2 to 10 tasks, one per repository, with the same `joint` id and `lead` on the first repository's task; each has its own branch, worktree and task, so Merge, Create PR, Compare and Remove work per repository. One chat runs in the lead's worktree with the others as additional folders (Claude Code's `--add-dir`), derived from the task store whenever it starts or resumes and never taken from the UI; any chat opened in the lead's worktree (by hand, or by `start_agent`) is the group's chat and gets them too; every task follows that chat's state. The group takes one slot of `agentTasks.maxParallel` and is queued and dequeued as a unit (**Start now** on any task starts all). Its first message is `jointPrompt` (the lead's description, which folder is which repository on which branch, a request to keep the change consistent and to commit in each folder). Each task's description is the item's title and body without the per-repository note, so the 8,000-byte limit is checked against that. Only Claude Code (and a defined agent that runs on it) can: Codex and custom ACP agents are refused before anything is created with "<agent> runs on <engine>, which cannot work in several folders at once: delegate per repository instead" and Delegate's "(the item says together: true; without that line each repository gets its own agent)". Every repository and every worktree must be trusted ("… is not trusted …"); a chat that resumes while one is untrusted or gone does not open. The approval policy treats the group's worktrees like the chat's folder (`Policy.autoApproves`). Removing one task stops the shared chat for the group (after asking), the others stay, the next task becomes the lead, and a group of one is an ordinary task (`NormalizeJoint`). A waiting start of such an item starts the group the same way, and the untrusted-project confirmation then says "It runs as one agent across the repositories api, web.".

- An item can name a workflow (`workflow:`, not with `together`): see [Workflows](#workflows) for how Delegate starts a run per repository and how the item's status follows the run.
- Not yet: milestones, budgets per item, people as assignees, watching a folder outside the workspace, importing from or synchronizing with trackers.

### Workflows

A workflow is a repeatable way to deliver a change: steps that agents, scripts and the user take in order. The feature is `internal/features/workflows` (optional: `features.enabled.workflows`, Settings ▸ Extensions ▸ Built-in; switched off, there is no panel, command, tool or `flint workflow`/`flint run` command). The design is [design/workflows.md](design/workflows.md), the guide is [site/guides/workflows.md](../site/guides/workflows.md).

- **The file**: one Markdown file, `.flint/workflows/<name>.md` in a repository (shared through git), `workflows/` of the config directory (personal) or built in (`feature`, `bug-fix`; `internal/features/workflows/builtin`); a project's file wins over a personal one, which wins over a built-in (`load.go`). Front matter has one key, `description`. Each `## Title` line starts a step; the lines right after it up to the first empty line are its keys, the rest is its text (`format.go`, pure). Keys: `type` (`agent` default, `script`, `review`, `gate`, `workflow`), `agent`, `run` (a run configuration's name), `on-fail` (an earlier `agent` step), `workflow` (the workflow a `workflow` step runs). Limits: 30 steps after sub-workflows are put in (at most 3 levels, no cycles), 64 KiB per file, 16,000 characters per step, 50 workflows per folder; the first step is an `agent` step; step ids are the titles as slugs and must differ; the character rules are those of project items. A file that breaks a rule is listed as a problem with the reason and is not offered. In Restricted Mode, repository workflows are counted and not offered.
- **The diagram**: **View** on a workflow in the Workflows panel (or clicking its name, *Show Workflow Diagram…* in the palette, or *Show Workflow Diagram* on a `.flint/workflows/*.md` file in the file tree) opens the tab "Workflow: <name>" (`WorkflowView.tsx`, tab kind `workflow-view`, restored with the session): the resolved steps as cards joined by arrows (kind, agent, a script step's run configuration and resolved command, "fails → back to X"), the selected step's text, and what script steps run with the sandbox state. It is the component the run tab and the Run Workflow… preview draw (`StepFlow.tsx`; rows wrap, and a narrow tab shows a list). **Run…** starts a run of it; **Open file** opens the file (not for built-ins). The view is read-only: a workflow is changed in its file.
- **Step kinds**: `agent` (a new chat in the task's worktree gets the step's text; passes when the agent ends with `RESULT: DONE`), `script` (the run configuration runs in the worktree in a run tab; passes on exit 0), `review` (a new chat of another agent reviews the change; passes on `RESULT: PASS`), `gate` (the run waits; passes when the user approves), `workflow` (the named workflow's steps take its place). `RESULT: BLOCKED`, or no result line, makes the run wait with the agent's last lines, because a turn that ends is not a step that is done.
- **A run** (`run.go`, pure and tested without Flint) has the states `running`, `waiting` (a gate), `failed` (a step failed and nothing sends the work back by itself), `paused`, `done` and `stopped`. Run Workflow… (palette, `＋` in the Workflows panel) asks for the workflow, the task and the agent, and makes one agent task (branch, worktree, queue, trust and budget pause of New Agent Task) that takes the steps in order. Every agent step is an ordinary chat tab of the task, every script step an ordinary run tab, and the result an ordinary agent task with Show diff, Merge and Create PR. The definition is copied into the run when it starts: editing `.flint/workflows` in the worktree changes nothing about that run.
- **Actions** (offered by Go per state, `Actions(run)`; the run tab is where a run is steered): **Approve** (`waiting`), **Send back…** with a note (`waiting`, `failed`, `paused`: the steps from the chosen agent step are taken again and the note goes to its agent), **Retry** (`failed`), **Continue anyway** (`failed`: the failed step counts as passed, after a confirmation), **Pause** / **Resume**, **Stop** (any but `done`: the running turn or script is stopped; the agent task stays), **Remove** (a run that is over; the task stays). Taking over needs no action: the step's chat is a chat; pause, work with the agent, resume.
- **Rework**: a `script` or `review` step that fails and has `on-fail` sends the work back to that step with the reason (the end of the script's output, or the reviewer's findings), and the steps from there are taken again, at most `workflows.maxAttempts` times per step (1 to 10, default 3); after that the run is `failed` and waits. The step card shows "Attempt n". That bound, `usage.pauseOverBudget` and Stop keep a loop from running away.
- **Limits** (`limits.go`): a usage limit is not a failure and counts as no attempt. Flint's budget (`usage.pauseOverBudget`) or the agent's provider refusing for quota (usage limit, rate limit, no credits) puts the run in `paused` with a `hold` (`kind` `budget` or `limit`); **Resume** takes the step again. `LimitKind` reads the error of a chat start, the error and last 5 lines of a failed turn, a first step's task error and the last 5 lines of a turn that ended without a result line; only whole phrases count. `workflows.fallbackAgent`: when the step's agent hit its own limit (not Flint's budget), this agent takes the step at once if it can start and is not the one that hit it; the run view shows "instead of …"; if it hits a limit too, the run is held. `workflows.resumeAfterMinutes` (0 to 720, default 0): a held run resumes by itself after that long, one timer per held run re-armed after a restart, at most 12 automatic resumes per step. Flint does not read when a provider's limit resets.
- **The Workflows panel** (activity bar, after Agent Tasks; `Show Workflows`): the runs in the groups Needs you, Running and Finished (collapsed), each row with its state badge and its primary action (Approve, Resume or Retry), and the workflows of the active folder with their source, steps, **Run…** and **Open**; problems; the schedules. Its header has Run Workflow…, Refresh and a menu with New Workflow…, Coordinate with Agent… and, when Projects runs, Open project board. The badge and the status bar item "Workflows: n need(s) you" count the runs with `needsUser` (a gate, a failure, or a hold that will not resume by itself). The run tab (`RunView`) shows a row of step cards with state, agent, kind and "fails → back to …", the step's text and the end of its output, **Open chat** / **Open run tab**, **Open task**, **Show changes**, the note the agent gets and the log. The Welcome screen offers Run a workflow…, Open the project board and New agent task… while the folder is open.
- **Project items** (`workflow: <name>` in an item's front matter; not with `together: true`): **Delegate** makes the item's agent tasks as usual, one per repository, and a run of the workflow takes each (`feature.NewAgentTask.Workflow`, `CreateAgentTasks` in `features_tasks.go`; every run is planned before any task is made, all or nothing). The first message is the project's context block, then the step's block, then the item's text. The item's status follows the **run**, not the task's turns (`feature.AgentTask.Run`): working while the run is `running` or `paused`, needs review when it waits at a gate or is `done`, failed when it `failed` or was `stopped`; every change of a run's state calls `Host.TasksChanged`. The panel shows "Workflow: <name>", the run's state and **Open run**. The workflow is read from the built-ins, the personal folder or the trusted checkout the task branches from, never from the project's folder; Delegate's confirmation for an untrusted project says so.
- **The coordinator** (`agenttools.go`, `agentsteer.go`): five tools on Flint's MCP server, offered only while the server and Settings ▸ Agent Context ▸ Actions ▸ **Run and steer workflows** (`mcpServer.actions.workflows`, off by default) are on and the folder is trusted: `list_workflows`, `get_workflow_runs`, `wait_for_workflow_run` (no polling; capped by `orchestration.maxWaitSeconds`) read; `start_workflow {workflow, task, agent?}` and `steer_workflow_run {run, action, step?, note?}` act. `action` is `pause`, `resume`, `retry`, `send_back` or `stop`, and nothing else: **an agent can never approve a gate or continue past a failed step** (`TestNoToolReachesApproveOrSkip`). Every acting call needs the user's yes to that one call (`mcpserver.Tool.Acts`: no "always allow"). A chat reaches the runs of its folder and, from a workspace folder that is in a Flint project whose folder is trusted, the runs of that project's items in any repository (`Host.FolderProjects`, answered by Projects); it starts at most 10 runs, and a chat that is a step of a run gets none of these tools. **Coordinate with Agent…** (`API.CoordinatePrompt`, which returns `toolOn` and `delegateOn`) puts a prompt into a chat draft (the user sends it): in a project's folder or repository, read the project with `get_project`, delegate ready items one at a time with `delegate_project_item`, start plain runs only for work that is not an item, wait, tell the user plainly when a run waits for approval and never try to approve, stop when the user says so; elsewhere, list the workflows, start runs, wait, tell the user when a run waits for approval.
- **Schedules** (`workflows.schedules`, at most 20, only in the user's own settings, never from a repository file): `name`, `workflow`, `folder`, `task`, `agent`, `at` (`HH:MM` local), `days`. One timer armed for the earliest due time (`schedule_timer.go`, no polling); `NextDue` (`schedule.go`) skips a time the clock skips and fires a repeated time once. A due schedule starts a run through the path of Run Workflow… (origin `schedule:<name>`, no dialog) and starts nothing, with one line shown in the panel, when its folder is not open or not trusted, its last run is not over, the usage budget pauses new turns or the start refuses. A missed time is not caught up (more than 5 minutes late: "missed at …"). The last outcome is kept in memory only.
- **A schedule runs what you saved**: Flint keeps a fingerprint of the schedule's resolved workflow and of the command lines of its script steps' run configurations, taken when it first sees the schedule after you saved it. When either changed (a repository's workflow file that overrides one of the same name, an edited `.flint/run.json`), the schedule starts nothing and says so; saving the schedule again or `AcceptSchedule` accepts the change. The timer re-arms every few minutes, so a computer that slept fires on time after waking, and follows a change of time zone.
- **What scripts run, and what they may not touch**: Run Workflow… and the agents' `start_workflow` confirmation show each script step's run configuration, its command line and whether the sandbox confines it (only the configuration comes from your checkout; what it runs is the agent's code). A script step may not change what later steps run or read at the top of its worktree (`.git`, `.claude`, `.codex`, `.flint`, `.vscode`, `.idea`, `.mcp.json`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md`): the macOS sandbox denies it, and on every system a change stops the run. A review step's chat loads none of the worktree's project settings or instruction files where its agent allows it (Claude Code, Codex) and asks for every edit and command. **Stop** ends every chat the run opened, and a stopped run's queued task never starts.
- **Sandbox** (`workflows.sandbox` `on` (the default) or `off`; `sandboxNetwork`; `sandboxWritable`, at most 10 folders): runs every `script` step in the operating system's sandbox that extensions use (`internal/extensions/sandbox`, `sandbox.BuildScript`; `sandbox-exec` on macOS, Landlock and seccomp on Linux). The script reads what the user can read except the protected places (SSH and GPG keys, cloud and registry credentials, `.netrc`, password stores, shell history, keychains, browser profiles, Flint's own folder), writes only in the task's worktree, the temporary folders and `sandboxWritable`, and uses the network only with `sandboxNetwork`. The run tab's first line says what is confined and what was asked for and not granted. It fails closed: with no sandbox on this system the step fails ("the sandbox is not available here …") instead of running unconfined, and says what to do: "switch off “Run script steps in a sandbox” in Settings ▸ Workflows to run it without one (Flint asks you once per folder)". A sandboxed step that exits non-zero gets one more line after its reason: "This step ran in a sandbox: it can write only in the run's folder and temp folders, and has no network. If the command needs a cache folder or the network, add the folder or allow the network in Settings ▸ Workflows." (the run's error, or only its log when the work is sent back automatically, so the agent's feedback does not carry it). **After you switch the sandbox off, script steps need your OK once per checkout**: the first start of a workflow with a script step there (Run Workflow…, `flint workflow run`, a project item's Delegate) asks in a native dialog, "Run scripts without a sandbox?", with the folder and each script step's command line; **Run without a sandbox** remembers the checkout (`workflowUnsandboxed` in `state.json`, at most 200 folders), **Cancel** (the default) starts nothing. An agent's `start_workflow` and a schedule never ask: they are refused (the agent is told to ask you to run the workflow once yourself) or skipped until you said yes there. Run Workflow… shows "You allowed scripts without a sandbox in this folder" with **Take back** (`Listing.unsandboxedOK`, `ForgetUnsandboxed`). With the sandbox on (the default) nothing is asked. **It does not confine agent steps**, only script steps. No cache folder is writable by default: a build that writes a global cache (Go's build cache, npm's) needs that folder in `sandboxWritable`, and a test that downloads needs `sandboxNetwork`. Known gaps (macOS Mach/XPC services stay reachable; on Linux `/proc` stays readable and an older kernel closes less) are in the design doc.
- **Security**: a script step names a run configuration that Flint reads from the checkout the run started from, never from the task's worktree; a workflow file cannot hold a command, an environment, a tool or a permission, only names of agents and run configurations; text sent to an agent is redacted, bounded and fenced (a line starting `=====` is quoted); a step's chat asks for permission like any chat, a workflow grants nothing. Bounds: 30 steps, `maxAttempts`, 12 automatic resumes per step, 100 runs kept, 200 log entries per run, 20 schedules, 10 sandbox folders.
- **Command line** ([reference](../site/reference/cli.md), described under [macOS integration](#macos-integration-wails-v3)): `flint workflow list | show | new | run | coordinate` and `flint run list | show | wait | approve | send-back | retry | skip | pause | resume | stop | remove` do what the panel and the run tab do. `flint run wait` exits 3 when the run needs the user. A command that acts is refused when an agent sends it, so `run approve` and `run skip` are the user's on this path too.
- **`run approve` and `run continue` ask in Flint**: whoever runs them, Flint shows its own dialog ("Approve this step?", with the run, the workflow, the step and the process that asked; Cancel the default) and acts only after your yes; otherwise `not approved in Flint`, exit 1. Commands that act are also refused to agents and to processes that are not in a terminal.
- **Stored**: runs are in `state.json` under `workflowRuns` (at most 100, the oldest by update pruned); the workflow files, schedules (settings) and the project items' `workflow` key are where the user put them. The definition of a run is a copy inside it.
- Not yet: parallel steps, artifacts declared per step, a run across several repositories, conditions other than pass or fail, reading when a provider's usage limit resets.

### Agents panel

- The Agents panel (✦ on the activity bar, or *Show Agents* in the palette) lists every agent of this window in one list: the open chats and the agent tasks. A row shows the state, the chat's first message (or the task's title), the agent, whether it is a task, and the folder. Clicking a row shows its chat tab; a queued task, which has no chat yet, opens the Agent Tasks panel.
- Order, most urgent first: waiting for you, failed, finished (the turn ended while you were in another tab), working, queued, idle. The header, and the ✦ button on the activity bar (`PanelSpec.useBadge`, whether the panel is open or not), count the agents that need you (waiting, failed, finished and not yet seen). A finished chat becomes idle once you show its tab; a failed one stays until the next turn.
- A turn is a turn whoever started it: Go's session manager emits `turn_start` for every prompt (`agentsession.Manager.Prompt`: one the user typed, a queued task's description, Delegate and automatic starts, joint groups, `start_agent` and `send_prompt`, Flint's notices), and the chat reducer marks the chat busy on it. So the waiting, finished-unseen and failed states, the reveal of hidden tabs and the notifications work for chats whose turns Go started. History a resumed chat replays comes before any `turn_start` and is never a request or a finished turn. A task chat takes its own transcript's state when that is newer than the task list (`taskChatState`), so a hidden task chat that starts waiting comes back while both the Agents and the Agent Tasks panels are closed. A queued task that can't start by itself carries the reason (`TaskView.blocked`: repository not open, worktree in Restricted Mode, its agent did not start the last time, budget pause) in its tooltip here and under its row in Agent Tasks. Every `turn_start` is followed by exactly one `turn_end`: when a driver fails before it ends the turn itself (a dead process, an unknown session, a closed connection) or is stopped meanwhile, the manager reports the error and ends the turn (`error`, or `cancelled` when stopped). A task whose chat opened but said nothing since its first message failed shows that failure, not idle (`agenttask.Combine` prefers the remembered state over idle chats; a turn the user starts clears it).
- States use the vocabulary of the Agent Tasks panel. A chat in a task's worktree shows the state Go derived for the task (`agenttask.Tracker`); other chats have no tracker, so their state is read from the transcript by the same rules (`lib/agentList.ts` `chatState`). A restored chat is idle until its next message. Tasks with no open chat are listed only while queued; finished and failed ones stay in the Agent Tasks panel.

- **Peek**: the *Peek* action on a row (or `⌘`-click on the row; Ctrl on Linux and Windows) shows that agent's chat in an overlay over the current tab, which stays the active one. Read it, answer a permission request or send a prompt, then close it with `Esc` or ✕; *Keep as Tab* closes it and switches to the chat's tab. Only one peek is open at a time, and a chat that is already the active tab is not peeked. The overlay reuses the chat view: the chat holds no event subscription of its own (events land in the chat store) and the draft lives in the store, so a chat shown in its tab and in the peek stays in step. What you read in a peek counts as seen. *Peek at Agent Needing Attention* in the palette peeks at the first agent in the panel's order that needs you, not counting the chat in front.
- **Hide until needed**: a chat tab's context menu (*Hide Until Agent Needs Me*) or the row's *Hide until needed* removes the tab from the tab strip. It comes back by itself, without taking focus, when its agent needs you (waiting, failed, or finished while the tab was not shown: the panel's states, `lib/settledTabs.ts`). A hidden tab is still open: it stays in the Agents panel (marked *hidden*, with *Show tab*), in the saved session and in Close All, and clicking its row shows and activates it. Hiding the active tab switches to a drawn neighbour; the only drawn tab, or an agent that already needs you, cannot be hidden. Closing a tab or going back never lands on a hidden one. The flag is saved in the session (`settled` on the chat tab, an optional field, so no snapshot version change) and a restored hidden chat stays hidden until its agent needs you.

### Agent context (Flint's MCP server)

- Chats started by Flint get Flint's own MCP server (`internal/mcpserver`, MCP over HTTP on `127.0.0.1`, standard library only) with read-only tools (`internal/mcptools`) and, when switched on, tools that act (below): `get_diagnostics` (language server problems), `get_editor_state` (open files, the active file and the selection), `get_test_results` (the last test runs), and, when turned on in Settings ▸ Agent Context, `get_terminal_output`. The Projects feature adds `get_project` (below, under Projects).
- Claude Code gets it through `--mcp-config`, Codex through `-c mcp_servers.flint.*` (only when the installed Codex supports HTTP servers), custom ACP agents in `session/new` when they advertise HTTP MCP support. Commit messages and inline edits don't get it.
- Every chat gets its own token (in `FLINT_MCP_TOKEN`, never on a command line), revoked when the chat ends or its folder closes; a token only sees its own folder. Requests from web pages are refused (Host and Origin checks), answers are redacted and bounded, and turning the server off closes its port.
- Diagnostics, editor state and test results count as reads (no prompt). Terminal output is off by default and always asks, because they can show anything, including what a command printed from outside the folder. Untrusted folders get no server.
- **Tools that act** let an agent do what you do in Flint's UI, so the result shows in Flint's own tabs as well as in the tool's answer. They are off by default, one switch per group in Settings ▸ Agent Context (`mcpServer.actions`), and a tool whose group is off isn't listed to agents at all:
  - `run_tests` (`actions.tests`): a Go package folder, a `_test.go` file or a JS/TS test file, optionally single tests, through the test runner like the gutter ▶. The run shows in the Tests tab; the tool waits up to `mcpServer.testWaitSeconds` (120 s) and answers with the totals and each failed test with its output, or with the results so far.
  - `run_configuration` and `get_run_output` (`actions.run`): starts (or restarts) a run configuration of `.flint/run.json` or a detected one, by name, in its run tab, and returns the run's id; `get_run_output` reads a run's last lines and whether it exited.
  - `send_http_request` (`actions.http`): a named request (`### name`) of a `.http` / `.rest` file in the folder, as saved on disk, with an optional environment; body files only from inside the workspace. The answer has the status, the headers (cookies hidden) and the first 16 KiB of the body; the response is kept in the file's response history.
  - `run_sql_query` (`actions.sql`, Database feature): one reading statement on a saved connection, by name, only when that connection is read-only; at most 500 rows (100 by default), recorded in the connection's query history.
  - `add_project_item` (`actions.projects`, Projects feature): adds one `todo` item to the backlog of a Flint project whose folder is trusted (see Projects); the approval shows what will be written. It can't change, delete, re-status or delegate items.
  - `delegate_project_item` (`actions.delegate`, Projects feature): delegates one ready item of a project the chat's folder is in, exactly as the Delegate click does (see Projects); the approval shows the item, its agent or workflow and where each task is made. An agent can delegate a ready item only when "Delegate project items" is on, only with the user's yes to that one call, never an item that waits for others, never from a project whose folder is untrusted, and never from inside handed-out work (an agent task's chat or worktree, or a workflow step).
- Every call of an acting tool needs your yes to that one call. When the agent asks in the chat (Claude Code), the permission card is the question: it has no "Always allow", and no approval policy answers it, not even "Do everything". When no such card was answered (Codex, custom agents, a Claude Code rule that allows the tool), Flint asks in a native dialog with the tool, what it would do and its arguments. Arguments are checked first (paths, tests, configurations and requests must exist in the chat's folder; nothing becomes a command line), and unknown arguments are refused.

### Agent orchestration (agents that start agents)

An agent chat can start other agent chats in the same folder, send them messages, wait for them and read their output, through Flint's MCP server. **It is off by default** (Settings ▸ Agents ▸ Agent orchestration, `orchestration.enabled`; Flint's MCP server must be on). While it is off the tools are not even listed.

- **The grant.** The first time a chat calls one of the tools, Flint asks once in a native dialog the web view cannot answer: which agent, which folder, how many agents (`orchestration.maxChildren`), how deep (`orchestration.maxDepth`), and that the messages it sends appear in their chats. A yes is a grant for that chat only, held in memory: it covers that project and nothing else, never an untrusted folder (Restricted Mode), stops working if the folder loses its trust or the setting is switched off, and ends when the chat is closed. Closing the chat (its tab, or `stop_agent` on it) also stops every agent it started, deepest first, and a child's copy of the grant works only while the grant of the chat you were asked about still exists, so closing the root really ends the run. Agents the chat starts inherit it one level down; an agent at the depth limit cannot start agents. If you say no, the chat is not asked again for as long as it exists. Under a grant the agent's own permission request for these six tools is allowed once per call; no other tool is allowed by it.
- **What you see.** Every agent started this way opens as its own chat tab without taking focus, and every message sent to an agent is shown in its transcript as coming from the sending agent, after redaction. Messages are not previewed first: that is the trade-off of a grant, in place of a question for each message. Every prompt still passes the usage budget (`usage.pauseOverBudget`).
- **Telling the parent** (`orchestration.notifyParent`, on by default). When an agent a chat started starts waiting for approval, fails or finishes, the chat gets one message, `[Flint] child <id> (<role>) is <state>:` followed by that agent's last 20 lines (redacted), so it need not poll. It shows in the chat as coming from Flint. It is sent when the chat is idle and you have no draft open there; otherwise it is held until the turn ends or the draft is closed or emptied. Notices are merged per child (a newer state replaces the queued one), at most 8 wait per chat, they are dropped when the chat is closed, and several waiting notices go out as one message. Only a change of state is news, and a turn that a notice itself started does not produce a notice when it ends (waiting for approval still does), so a notice cannot set off another notice on its own.
- **A budget of turns without you** (`orchestration.maxAutoTurns`, 40 by default, at most 400). Agents can start turns in each other three ways: `send_prompt`, the first prompt of `start_agent`, and a delivered `[Flint]` notice. Flint counts every such turn in the group of chats that one grant covers (the chat you were asked about and everything below it) since the last message you typed in any chat of that group. Past the budget, `send_prompt` and `start_agent` fail with a message telling the agent to stop and report to you, and notices are dropped instead of delivered; typing a message in any chat of the group starts the count again. What this bounds: the number of agent-to-agent turns between two messages of yours. What it does not bound: how long or how expensive each turn is (that is the usage budget, `usage.pauseOverBudget`, which is off by default), turns you start yourself, and chats outside the grant's group.
- **Limits.** `maxChildren` agents per chat (up to 16), `maxDepth` levels (up to 4), one wait at most `maxWaitSeconds` (up to 600, which is also the MCP server's cap on a call), `outputLines` lines of output per read. Agents only reach chats whose folder is the chat's workspace folder (or inside it) or a worktree of a task of its repository, and of those only themselves and the agents they started, and theirs: a chat you opened, the caller's parent and its siblings are out of reach (not listed, not readable, not waitable).
- **The tools.**
  - `list_agents`: the caller and the agents it started, and theirs, with id, agent, role, state, parent, depth and folder. Agent CLIs running in terminal tabs (see *Status of agents in terminal tabs*) are not listed: a tab has no link to the chat that might have started it, so it cannot be attributed to the caller, and the other tools refuse a terminal id with a message saying so. The Agents panel still shows them to you.
  - `start_agent {agent?, role?, task, worktree?, base?}`: starts a child and sends it the task (a role's text from `<config>/roles/*.md` or the trusted folder's `.flint/roles/*.md` is put before it). The agent defaults to the role's, else the caller's; a role limited to `claude` or `codex` also fits a defined agent on that engine. With `worktree: true` Flint first makes one task (branch and worktree, `base` defaulting to the project's current branch) in the caller's repository and starts the child there; it is listed in the Tasks panel like any task. It needs a trusted project, and is refused (not queued) while `agentTasks.maxParallel` tasks are already working. The tools reach chats in the project folder and in worktrees of tasks of the same repository, nothing else; the child limit and depth limit apply as for any child.
  - `send_prompt {id, text}`: to the agents the caller started, and theirs. Refused, with nothing sent, while the target waits for your approval, while you have a draft open in its chat, or while it is working.
  - `wait_for_agent {id, until, timeoutSeconds}`: for the caller itself or its descendants; blocks (no polling) until the agent is `idle`, `waiting`, `finished` or `failed`, and returns `{state, error, timedOut}`.
  - `read_agent_output {id, lines?}`: for the caller itself or its descendants; the last lines of the agent's text and tool-call titles, redacted, from a 64 KiB buffer.
  - `stop_agent {id}`: stops one of the caller's descendants and everything it started.

### Commit messages and conflicts

- ✦ *Review* ("Review Changes with Agent", also in a diff tab and the palette): the review agent (`agentReview.agent`, else the default agent) runs headless, like *Generate message*, on the ticked changes (`agentReview.scope`: or all; a diff tab adds its file), HEAD against the working tree. Go keeps only the requested paths `git status` reports as changed (with git's kinds and rename sources), in a repository that is an open folder or the work tree of one. Diffs come from one `rev-parse` and batched `git diff` calls split per path (an unpaired rename's source stays its own section). `internal/review` renders each file's diff with the new version's line numbers within a strict `agentReview.maxDiffKB` (small diffs whole; larger ones keep their first hunks or a one-line summary; files with no room are listed in a note; untracked files are read only as far as their share), cuts text before redacting it (with a margin), drops NUL bytes and leaves out credential files (`redact.SecretFile`); untracked files are read only as regular files inside the repository (no symlinks). Claude Code gets Read/Grep/Glob with `--disallowedTools Read(...)` rules for credential files (`agent.HeadlessDenyRules`); Codex's read-only sandbox can still read any file the user can; a custom agent's own tools are outside Flint's control, and one started with an auto-approve flag (`settings.AutoApproveArgs`) gets a warning in Settings and in the review's notes. The agent answers with JSON findings (file, line, end line, severity, title, explanation, optional replacement); `review.Parse` tolerates prose, fences, a bare array, other key names and a cut-off answer, drops findings about other files, caps their number and sizes, strips control and format (Cf) characters and redacts secrets; only files with findings are read afterwards to place them. Findings show in the Commit panel (counts per severity; a click opens the diff at the line) and as thread widgets under their lines in the diff tab (`lib/prThreadWidgets.ts`). Each keeps its line and neighbours: when the file changes it moves with its line, or is marked stale and shown above the diff (`lib/agentReview.ts`). ✦ *Fix it* / *Fix all* fill the agent chat's draft with the findings quoted as the reviewer's output (Fix all: the 20 worst) and the code around each; *Dismiss* removes one. *Cancel* (or `agentReview.timeoutSeconds`) stops the agent's process group.
- ✦ *Generate message*: `claude -p` (or `codex exec`) receives the diff of the selected files and recent commit messages; the result lands in the message field for you to edit. A custom agent gets the same prompt in a one-shot ACP session in the repository: Flint serves reads inside it, declines every permission request and refuses writes sent through it; what the agent does with its own tools and its own configuration (for example a setting that lets it edit without asking) is outside Flint's control. The text after its last tool call is the message.
- ✦ *Resolve with claude*: merge conflicts are handed to an interactive agent session in a new terminal. The agent runs `git add` but does not commit. A custom agent has no interactive terminal mode, so when it is the default the first installed native agent (Claude Code, then Codex) does this, and the button names it; with no native agent installed the button is hidden.
- Nothing requires accepting diffs.

## Git and GitHub

### Git (IntelliJ-style)

- Commit panel (`⌘K`) with checkboxes, Amend, Commit and Push, and Rollback. Side-by-side diff in a tab.
- The ↶ button on the "Changes" and "Unversioned Files" group headers rolls back all ticked files of that group at once. For unversioned files this deletes them from disk, after a confirmation ("Delete N unversioned files?").
- Changed-line markers in the gutter, which also show what the agent touched.
- Branch widget in the status bar: checkout, new branch, fetch, pull, push (`⇧⌘K`).
- **Update Repository (pull)**: from the palette, the ⤓ button in the Commit panel, or the Branches popup. With one repository the pull starts at once. With several repositories in the workspace (like "Attach project" in IntelliJ) a chooser lists each one by folder name, with its branch and the number of commits to pull. The repository shown in the Commit panel is preselected, and an **All Projects** entry updates every repository in turn. Arrow keys and Enter work in the chooser.
- A commit during a merge includes the whole index.
- **Merge editor** for conflicted files (merge, rebase, cherry-pick, stash pop): *Resolve…* in the Commit panel, which also shows the conflicts left in each file. The file as git left it (clean hunks merged), each conflict an inline block with Accept Current / Incoming / Both (in either order) and ✦ Ask Agent (the block with both sides and its base from the index stages in the chat draft), or edited by hand. Labels say what current and incoming are for the operation: in a rebase, current is the branch being rebased onto and incoming your replayed commit. Next/previous conflict, Δ Current / Δ Incoming against the base, Save, and *Mark as Resolved* (save + `git add`, with a confirmation if markers remain). Shortcuts `⌥⌘N`/`⌥⌘P`, `⌥⌘1`–`⌥⌘4`, `⇧⌘↵`, all rebindable.
- **Annotate** (blame): a column with date and author next to every line (*Blame* button in the status bar, or right-click on the editor gutter), with a tooltip (full hash, author, date, message). Click opens the change from that commit. Uncommitted lines (including unsaved ones) show "Not committed".
- **Show History** of a file (`git log --follow`, including renames) in its own tab: the list of commits, the diff of the selected commit below it, and *Compare with current*.
- **Stash** in the Commit panel: save with a message (optionally including untracked files), and a list with Apply / Pop / Drop (with confirmation) and a diff of each file.
- Works for files in nested worktrees too.

### Worktrees

List, create (`<repo>.worktrees/<branch>`), remove, switch, open in a new window, or open directly with a terminal for an agent. Checkouts and commits made in a terminal refresh the UI, because the git directory is watched as well.

### GitHub pull requests

PR review inside the IDE through GitHub's REST and GraphQL APIs (`internal/github`), with the token of the account signed in under **Settings ▸ Accounts**; `gh` is not needed.

- **Accounts** (`internal/accounts`, `api_accounts.go`): *Sign in with GitHub* is the OAuth device flow (code shown in Flint, *Copy Code & Open GitHub*, polling that honours `interval`, `slow_down`, `expired_token`, `access_denied`); the OAuth App's client ID is `github.clientId` (empty until the maintainer registers one; Settings explains how). *Use the GitHub CLI's Token* runs `gh auth token` once after a native confirmation and stores it like a signed-in token. `GH_TOKEN` / `GITHUB_TOKEN` (`GH_ENTERPRISE_TOKEN` for a server) from the environment is used while no account is signed in, never stored. Tokens live only in the keyring (`flint-accounts`); `state.json` keeps login, avatar, host and scopes. *Sign Out* deletes the token and links to GitHub's authorized apps page for revoking. Providers register themselves (`accounts_registry.go`), so another one (Google) is one more registration.
- **GitHub Enterprise**: `github.host` (API at `https://<host>/api/v3` and `/api/graphql`, `<name>.ghe.com` too); each host has its own account.
- Wherever a GitHub feature finds no account it offers *Sign in with GitHub* in place (the view, a PR tab or diff, *CI: Sign in* in the status bar, a dialog for Fix with agent, Rerun and Create PR).

- **Pull Requests** view (⇅ icon on the activity bar, or "Pull Requests…" in the palette) lists the PRs of the active tab's repository.
  - Filters: *All / Created by me / Review requested* and *Open / Closed / Merged / All states*.
  - A search box narrows the loaded list by title or number: every word must be in the title (any case) or the number, and `#12` means a number that starts with 12. Nothing is fetched for it, so it finds only pull requests the filters loaded; Esc clears it.
  - Right-click a PR in the list for the actions of its tab's header without opening it: *Open*, *✦ Review with Agent*, *✦ Address Review Comments* (both put a draft in the agent chat; ⌥-click sends it right away), *Check Out* (open PRs only, asks first), *Open on GitHub*, *Copy Link* and *Copy Number*.
  - **✦ Review with agent** in the PR tab's header (also "Review Pull Request with Agent" in the palette for the active PR tab or the current branch's PR) puts a request for a code review in the agent chat of the PR's folder as a draft; ⌥-click sends it right away. The draft names the PR, its branches and URL and tells the agent to read the change itself (`gh pr diff`), to treat the PR's text as data, to report findings in the chat, and to change no files and post nothing to GitHub. The title goes in as one line of at most 200 characters.
  - Each PR shows CI state (✓ / ✗ / ●, with counts of passed, failed and running checks in the tooltip), review decision (Approved, Changes requested, Review required, Draft, Merged) and time of last update.
  - Without an account it offers *Sign in with GitHub*; without a remote on the configured host it says so. The repository is the remote marked by `gh repo set-default`, else `upstream`, `github`, `origin`, then the rest.
- Clicking a PR opens a PR tab: title, branches, author, an expandable list of checks with links, description (Markdown rendered in Go, no raw HTML), files with +/− and the number of open threads, commits, reviews, plus *Check out* (`git fetch <remote> pull/N/head`, then the PR's branch created or fast-forwarded, `<owner>/<branch>` for a fork's, a diverged branch left alone; refuses when tracked files have uncommitted changes) and *Open on GitHub*.
- Clicking a file opens a side-by-side diff (merge base ↔ head, as on GitHub) with **inline comments**:
  - A thread under the line with reply (`⌘↵`) and *Resolve* / *Unresolve*. The other side gets a spacer of the same height so the sides stay aligned.
  - `+` in the gutter on lines GitHub allows comments on (inside hunks) opens a new comment: *Add single comment* (posted immediately) or *Start a review* / *Add review comment* (a pending review visible only to you).
  - Outdated threads and file-level comments are shown above the diff.
- *Submit review* bar (in the PR tab and in the diff): a summary plus *Comment*, *Approve*, *Request changes*; with a pending review, the number of comments and *Discard*.
- **A failing CI hands itself to the agent.** The checks of the current branch's PR and of agent tasks' PRs are followed (REST: the branch's PR, its check runs, statuses and workflow runs, all conditional requests, so a poll that finds nothing new costs no rate limit): read when the folder opens, on a branch switch, after push/fetch and when you return to the window, and polled only while a check is running (`ci.pollSeconds`, default 30 s, backing off ×1.5 up to 8×; in the background only for notifications). A failure shows a red **✗ CI** badge in the status bar with **Fix with agent**, a *Your branch* banner in the Pull Requests view, actions on each failed check in the PR tab, and **✗ CI** / **✦ Fix CI** on the task row.
  - **Fix with agent**: Go reads the run and its jobs, and each failed job's log (`GET …/actions/jobs/{id}/logs`, which redirects to a log URL fetched without the token; the last 8 MB), keeps the failed steps' lines (by the steps' start and end times), finds the failing step, keeps its last `ci.logTailLines` lines plus up to `ci.logErrorLines` error lines (go test, compilers, tsc, node:test/jest, pytest, cargo, npm, `##[error]`), redacts it (`internal/redact`), and maps `file:line` references to workspace files (runner paths by suffix, go test's bare file names through the failing packages and `go.mod`). The draft names the workflow, job and step, has the excerpt, the files, the run and job links and the branch and commit, and lands in the right folder's chat (a task's own chat and worktree); the user reviews and sends it.
  - **Log**: the failed steps in a tab, with links that open the workspace file at the line. **Rerun**: `POST …/actions/runs/{id}/rerun-failed-jobs` after a native confirmation.
  - A notification when the PR's CI fails or turns green while Flint is in the background (`ci.notify`, with `notifyInBackground`).
- **Review comments hand themselves to the agent** (`api_pr_agent.go`, `internal/prfeedback`, `store/prAgent.ts`), the same way a failing CI does:
  - **✦ Ask agent** on every unresolved thread (under its line in the diff, and on outdated and file-level threads above it) puts that thread in the agent chat draft: the PR's number, URL and branches, the file and line (or range), the comments in order with their authors, each GitHub `suggestion` block called out as the reviewer's proposed replacement for those lines, and the code around the line.
  - **✦ Address review comments** in the PR tab's header (shown while the PR has unresolved threads or a standing "changes requested" review; also "Address Review Comments with Agent" in the palette for the active PR tab or the current branch's PR, **✦ Address** in the *Your branch* banner and **✦ Review comments** on a task row with an open PR) gathers every unresolved, non-outdated thread, grouped by file in the PR's file order and then by line, plus the body of each review that requests changes and still stands (not approved or dismissed since). At most `prReview.maxThreads` threads (20) and 64 kB go into one draft; the rest are listed by `file:line` at its end ("address these first, then ask for the rest"), and outdated threads are counted.
  - The code comes from the working tree (`prReview.contextLines` lines on each side, 8; 0 leaves it out) only when the folder has the PR's branch checked out (the branch *Check out* names, or the PR's head commit; a fork's branch under its own name only when it contains that commit) and the file is a regular file inside the open folder; otherwise, and for comments on the base side, it is the hunk of the PR's diff. Credential files (`redact.SecretFile`) are never shown, symlinks are not followed.
  - When another branch is checked out the draft says so in its first lines and tells the agent to edit nothing until the PR's branch is checked out; such a draft is never sent by ⌥-click, and a toast points at *Check out*.
  - Everything a reviewer wrote (and the PR's title) is quoted with `> ` and declared untrusted data, with control and format characters removed, secrets redacted (`internal/redact`) and bounded: 4,000 bytes per comment and suggestion, the first and the latest 7 comments of a thread, the latest 5 change requests. The draft is built in Go from the PR already loaded (Go's 30 s cache; one refetch when a thread isn't in it); nothing polls, nothing is posted to GitHub, and nothing is sent until the user presses Send (⌥-click sends right away). The draft goes to the chat of the folder the PR is checked out in; a task's goes to the task's chat and worktree.
- Apart from running CI checks, nothing refreshes in the background. The list loads when the view opens and when you return to the window; a PR loads when its tab opens and when you return to the window; both also refresh with ↻. Go caches responses in memory for about 30 seconds. Reads that GitHub answers with `Retry-After` wait up to `github.maxRetryWaitSeconds` (60) and try once more; longer waits and a used-up hourly limit are reported with the time to retry.

## Run, test, debug and profile

### Run configurations (IntelliJ-style)

- Configurations live in `.flint/run.json` (meant to be committed, like `.idea/runConfigurations` or `.vscode/launch.json`). Types:
  - `command`: a program with arguments, or a shell line;
  - `go`: build a package or file, then run the binary;
  - `npm`: a `package.json` script; the package manager is chosen from the lockfile;
  - `make`.
- Working directory, environment variables and a "before launch" step.
- Without configurations Flint detects Go `main` packages, `Makefile` targets and `package.json` scripts on its own (they are written to the file only after you edit them).
- Selector with ▶ Run / ↻ Rerun / ■ Stop in the title bar. Output goes to a tab with xterm.js and clickable `path:line`.
- The process runs in a PTY in its own process group, so Stop (SIGINT, then SIGKILL after 3 s) also ends child processes (`go run`, `npm run`).
- The `debug` field is reserved for the DAP debugger (`dlv dap`), and `profileURL` points at the program's `net/http/pprof` endpoint for profiling (see [Profiling](#profiling-go)).

### Tests

- ▶ in the gutter next to `func TestXxx`, `t.Run("…")` subtests, and `describe` / `it` / `test` in `*.test.ts(x)` / `*.spec.*`.
- ▶ next to `package` (or on line 1 of a JS file) runs the whole file; `⌥`-click runs the whole package.
- The result is shown next to each test: ✓ / ✗ / ↷.
- *Tests* tab: a tree of packages and tests with status and duration, failure output with clickable locations, "Rerun failed", and rerun of a single test.
- Go: `go test -json`, parsed in Go. JS: `node --test --test-reporter=tap` (also through the repository's `test` script, `webbuild --test`). Other runners (jest, vitest) run through the `test` script and report only the exit code.

### Debugger

- Go through Delve (`dlv dap`; the DAP client is written in Go: `internal/dap`).
- The bug button next to ▶ in the title bar (`⌃D`) debugs the selected `go` configuration; `⇧`-click on ▶ next to a test debugs that test.
- Breakpoints: click in the gutter of `.go` files, or `⌘F8`. They move with edits and are part of the saved session.
- When stopped, the editor shows the current line, and the *Debug* tab shows stack frames, variables (expanded lazily) and a console with program output and expression evaluation.
- Stepping: `F9` resume, `F8` step over, `F7` step into, `⇧F8` step out, `⌘F2` stop.
- Requires `dlv` (`go install github.com/go-delve/delve/cmd/dlv@latest`) and macOS developer mode (`sudo DevToolsSecurity -enable`).

### Profiling (Go)

- **Tests** (the main path): "Profile Tests in File" / "Profile Package Tests" in the ▶ menu in the title bar, in the palette, in the file tree menu (Profile Tests), and on right-click of a gutter ▶ (also for a single test). Flint runs `go test -cpuprofile … -memprofile … -o …` (one package at a time) in the *Tests* tab, with the profiles and test binary in a temporary directory. When it finishes, a profile tab opens with CPU and memory (`alloc_space`, switchable to other sample types).
- **Configurations**: Go programs do not profile themselves, so "Profile '<configuration>'" requires the `profileURL` field (a `net/http/pprof` endpoint such as `http://localhost:6060/debug/pprof/profile?seconds=10`; without `seconds`, 10 s; localhost only). Flint starts the configuration if it is not running, waits until the program is listening, and fetches the profile. Without `profileURL` it opens the configuration editor.
- Any `.pprof` file can be opened too ("Open Profile File…").
- Go parses the profile (`github.com/google/pprof/profile`) and builds a call tree with flat/cum values, dropping frames below 0.5% of the total (a few dozen KB reach the UI).
- The profile tab (loaded lazily) draws a flame graph on a single `<canvas>`:
  - tooltip with function, `file:line`, flat/cum and %;
  - click zooms into a frame (ancestors stay at the top and zoom out); `Esc` / Reset Zoom goes back;
  - `⌘`-click or double-click opens the source at that line;
  - search highlights functions and shows their share.
- The *Top* view is a table of functions (flat, cum, %, sortable). "Raw .pprof" copies the path or reveals the file in Finder (for example for `go tool pprof`).
- Colors come from the theme (`--flame-*` in `style.css`).

## Databases

### Connections and browsing

- PostgreSQL (`pgx`) and ClickHouse (over its HTTP interface, `internal/clickhouse`, standard library only; default port 8123, or 8443 with TLS).
- ClickHouse: queries are POSTed and rows stream back as `JSONCompactEachRowWithNamesAndTypes`, decoded one row at a time, so the row limit stops the transfer. 64-bit integers beyond JS's exact range and all Decimals are exact strings (Decimals keep their scale), date-times carry their zone offset, arrays, maps and tuples are shown as JSON. The user and password go in `X-ClickHouse-User` / `X-ClickHouse-Key` headers and the database in `X-ClickHouse-Database`, never in the URL. Each SQL console has a `session_id` (so `SET` and temporary tables persist; one hour idle timeout) and each run a `query_id`: Cancel, and the row limit, run `KILL QUERY` and close the request. A read-only connection also sends `readonly=1`. Errors (`Code: N. DB::Exception: …`) are parsed, including those that arrive after the first rows. Responses are gzip-compressed except on loopback.
- Native ClickHouse profiles from older versions are moved to the HTTP port on first start (9000 → 8123, 9440 → 8443; a custom native port becomes the default HTTP port). The old `connections.json` is kept as `connections.json.native-backup` and a one-time notice lists the changes.
- Passwords are stored in the macOS Keychain, not in files.
- Under each connection, a "Databases (N)" node lists all databases on the server, as in pgAdmin. Postgres excludes templates, and databases without the `CONNECT` privilege get a red cross. ClickHouse shows what `SHOW DATABASES` returns.
- Expanding a database opens a separate pool to it (same host, user and password) and shows its schemas and tables.
- Right-click in the tree opens a context menu at every level: a connection (new SQL console, refresh, edit, copy its name or a password-less connection URL, delete), a database (new SQL console, refresh schema, copy name), a schema (copy name), a table (preview data, count rows, copy its name, qualified name or column list, quoted for the dialect) and a column (copy name, or name and type).
- Flint closes pools for non-default databases after one minute of inactivity, and immediately before a modifying statement (for example `DROP DATABASE`) so its own connections do not block the server.
- The SQL console has a database selector next to the connection, and the scratchpad remembers the choice.
- The database in a profile is only a default and is optional. Without it Flint connects to `postgres` (ClickHouse: `default`).
- SQL autocompletion from the selected database's schema; read-only mode.

### Query history

- Go records every executed statement (including failed ones, EXPLAIN, and edits from the results table) per connection and database: text, start time, duration, row count and error.
- The *History* button in the console or "Query History…" (`⇧⌘H`) opens the list, newest first, with a fuzzy filter (computed in Go; at most 300 entries reach the WebView), an "All databases" toggle and actions: `↵` inserts into the editor, `⌘↵` runs again, `⌘C` copies.
- The last 5000 statements per connection are kept.
- Passwords in `CREATE/ALTER ROLE … PASSWORD '…'` and ClickHouse `IDENTIFIED … BY '…'` are masked; otherwise the text is stored as is (statements longer than 256 KB are truncated).

### EXPLAIN

- *Explain* (`⇧⌘E`) and *Analyze* (`⇧⌘A`) in the console toolbar and the palette.
- Postgres: `EXPLAIN (FORMAT JSON)`, and with Analyze `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Go parses the JSON (`internal/db/explain.go`) into a tree of nodes with type, relation, index, cost, estimated and actual rows, loops, time, buffers and filter.
- The view is an expandable tree with a bar showing each node's share of total self time (Analyze) or self cost (estimate). Clicking a node shows details (conditions, sort keys, buffers).
- Warnings: a Seq Scan reading at least 10k rows (without Analyze: at least 10k estimated rows or cost of at least 2500), a row estimate off by 10x or more, and a sort or hash spilling to disk.
- ANALYZE always runs the statement in a transaction that is rolled back at the end. Before a statement other than SELECT (for example `DELETE`, `WITH … UPDATE`, `SELECT … INTO`) Flint asks for confirmation (Go decides, `ExplainResult.needsConfirm`). On a read-only connection such a statement is rejected.
- EXPLAIN uses the extended protocol, so it accepts only one statement.
- ClickHouse: `EXPLAIN PLAN indexes = 1` or (Analyze → *Pipeline*) `EXPLAIN PIPELINE`, shown as a tree built from indentation (best effort). Neither executes the query.

### Editing results

- Postgres: when all table-backed columns of a result come from a single table (the table OID from pgx `FieldDescriptions`, no extra query), the console fetches that table's columns and primary key from `pg_attribute` / `pg_index` in the background after showing the results.
- If the table has a primary key and all of its columns are in the result, cells become editable: double-click or `↵` / `F2` opens a type-aware editor (text, number with validation, boolean as a list, JSON in a multi-line field with validation, a NULL toggle). "+ Row" adds a row (unfilled columns get DEFAULT), "− Row" / `⌘⌫` marks a row for deletion.
- Changes are local and highlighted until submitted. *Revert* discards them; *Submit…* shows the generated SQL and, after *Apply*, runs `UPDATE` / `INSERT` / `DELETE` by primary key in a single transaction.
- Identifiers are quoted and checked against the catalog. Values are sent only as parameters (`$n::text::type`, so the server parses them like a literal). An `UPDATE` / `DELETE` that does not hit exactly one row rolls back everything.
- Computed columns, `GENERATED ALWAYS AS IDENTITY`, arrays and `bytea` are read-only. So are join results, views without a key, and read-only connections.
- ClickHouse: read-only.

## HTTP client

IntelliJ-style `.http` / `.rest` files with requests to your own APIs.

### File format

- Requests are separated by `###` (with an optional name).
- The request line is `METHOD URL [HTTP/1.1]` (no method means GET, no scheme means `http://`). A long URL can continue on indented lines starting with `?` / `&`.
- Then headers, an empty line and the body: inline, or from a file with `< ./body.json` (path relative to the `.http` file; `<@` also substitutes variables in it).
- Comments `#` and `//`. Directives: `# @name name`, `# @no-redirect`, `# @no-cookie-jar`, `# @timeout 60` (seconds, or for example `2m`).
- Variables `{{name}}`:
  - from `@name = value` lines (they apply to requests below the definition and take precedence);
  - from the environment in `http-client.env.json` and `http-client.private.env.json` next to the file (a `$shared` section applies to all environments; the private file overrides the public one);
  - dynamic: `{{$uuid}}`, `{{$timestamp}}`, `{{$isoTimestamp}}`, `{{$randomInt}}` (0–1000).
- Syntax highlighting, ▶ in the gutter next to every request, live syntax errors, and on send also unknown variables, always with a line number.

### Sending requests

- A request is sent **only** on an explicit action: `⌘↵` in a `.http` file (in SQL consoles `⌘↵` still runs the query), ▶, or "Send Request".
- A bar above the editor: environment, "Follow redirects" and ▶ Send.
- Go sends the request (`net/http`): 30 s timeout, Cancel, a separate cookie jar per file, and readable TLS errors.
- The response opens in a tab right after the file: status, time, size, collapsible headers, and the body in a read-only editor with JSON / XML / HTML highlighting (Go formats JSON; the type comes from `Content-Type` or is detected from the body). For bodies over 5 MB the beginning is shown, and "Save to file" writes the whole body.
- "Copy as curl" and a history of the last few responses for each request (in memory only, with a limit).
- Palette: "Send Request", "New HTTP Request File", "Select HTTP Environment", "Copy Request as curl", "Toggle HTTP Follow Redirects", "Clear HTTP Cookies".

**Add `http-client.private.env.json` to `.gitignore`**: it holds secrets (tokens, passwords). Flint does not write headers or variable values to its logs.

## Settings and macOS integration

### Settings

`⌘,` (flint menu ▸ Settings…, or "Settings…" in the palette) opens a settings tab with Appearance, Editor, Terminal, Accounts, Agents, Agent Context, Usage, AI in the Editor, Language Servers, File Watching (Linux only), CI, TODO List, Keymap, Updates, Extensions and Import sections, then a page per installed extension with settings. Every change applies immediately, without a restart, and saves itself (agent settings apply to sessions started afterwards).

- **Theme**: Dark, Light or System (follows the macOS appearance, `prefers-color-scheme`). Colors are CSS variables in `style.css` (`:root` and `[data-theme="light"]`); terminals have their own palette (`lib/terminalTheme.ts`); Go switches the title bar and window buttons (`NSApp.appearance`). The theme from the last run is applied before the first render (a copy in `localStorage`, and the window appearance set in Go before the window is created), so a light theme never flashes dark.
- **Editor**: font family, size and line height for all CodeMirror editors (files, diffs, scratchpads); optional save on window focus loss; optional format and organize imports on save, through the file's language server.
- **Terminal**: font, size and line height for terminals and run consoles (xterm refits immediately and the PTY gets the new size); and [background terminals](#background-terminals), the one setting that applies at the next start.
- **Agents**: the default agent for new chats, commit messages and conflict resolution (a custom agent can be the default; conflicts then go to a native agent). Per agent (Claude Code, Codex): the executable (empty = looked up on the login PATH; otherwise a command name or an absolute path, never one relative to the folder), the model (empty = the CLI's default), the model of each tier for defined agents (Fast, Balanced, Strong model; empty = the default, Claude Code's `haiku`, `sonnet`, `opus`, none for Codex) and extra command-line arguments, one per line. Extra arguments go before Flint's own flags, so Flint's flags are parsed last and win; arguments that name a flag Flint sets (the stream protocol, the permission prompt and mode, `--setting-sources`, `--settings`, `--resume`, `--model`; for Codex the sandbox, approval policy, `--yolo`, `--listen` and `-c approval_policy/sandbox*/projects*`) and `--` are refused, as are newlines, more than 32 arguments or arguments over 512 characters. In Restricted Mode the extra arguments are left out entirely, since a flag such as `--mcp-config` or `--add-dir` with a relative path would load the folder's files. Changes apply to new chats, commit messages and conflict resolution; running chats keep their settings. Custom ACP agents are added, edited, checked and removed in the same section (see [Custom agents (ACP)](#custom-agents-acp)). The same section lists the [defined agents](#defined-agents) with **New Agent…** and **Open**. *Review* sets what Review Changes with Agent covers (ticked or all changes), its agent, the largest diff it sends and its time limit (`agentReview`). Notifications are set here, with their delivery status and Send Test Notification.
- **Language Servers**: per language (Go, TypeScript/JavaScript, Python, Rust): on/off, which server (a known server's name such as `pylsp`, an absolute path to one, or another server; empty tries the known servers in order) and extra arguments, added after the server's own (`--stdio`). A change restarts that language's servers for the open files. Restricted Mode still applies: servers that run the folder's code and servers Flint doesn't know start only in trusted folders, and extra arguments are ignored there. typescript-language-server, also under another name or path, is always pinned to its own TypeScript, and `--tsserver-path` is refused.
- **Keymap**: a searchable list of all commands (by name or by shortcut, for example `⌘K`). Click a shortcut and press a new combination to change it; conflicts with other commands are shown, `↺` restores the default and `✕` removes it. Shortcuts handled by CodeMirror (`⌘F`, `⌘S`, `⌘↵`, and so on) are display-only. Overrides go into a layer of the command registry (`lib/commands.ts`), so the palette and the dispatcher use the effective shortcuts.
- **Updates**: the daily release check (see [Update check](#update-check)) can be turned off, and with it the "What's New" tab; **Check Now** checks right away.
- **Agent Context**, **Usage** and **AI in the Editor**: see [Agent context](#agent-context-flints-mcp-server), [Usage and budgets](#usage-and-budgets) and [AI in the editor](#ai-in-the-editor).
- **Import** ("Import from VS Code…" in the palette): reads VS Code's, Cursor's or VSCodium's `settings.json`, `keybindings.json` and active color theme (from its extension, following `include`), and shows what it would change and what it skips and why (chords, `when` clauses, settings Flint doesn't have, built-in themes). Nothing is written until you confirm. An imported theme becomes `theme: "custom"`: a palette over the dark or light base, limited to Flint's own color variables and hex colors, plus the theme's terminal colors (`terminal.ansi*`, background, cursor, selection).
- **Extensions**: see [Extensions](#extensions). Their color themes appear under Appearance ▸ **Color theme** and as **Use …** buttons on the extension; choosing one copies it into the custom theme (interface, editor and terminal colors), checked by the same Go rules as an imported theme.
- **Trusted folders**: see [Restricted Mode](#restricted-mode-workspace-trust).

### macOS integration (Wails v3)

- **Drag from Finder**: a folder dropped on the window opens in the window (or is attached to the workspace when one is already open); a file opens in a tab (up to 20 at a time). While dragging, the window shows what will happen.
- **Single instance**: `flint <folder>` with Flint already running hands the folder over (relative paths resolve from the calling directory) and brings the window to the front. A Flint with a different `FLINT_CONFIG_DIR` (for example a dev build) is a separate instance.
- **Command line** (`internal/cli`, [reference](../site/reference/cli.md)): `flint workflow …`, `flint run …`, `flint project …` and `flint task …` do what the Workflows, Projects and Agent Tasks panels do, against the running Flint, with plain text or `--json` and exit statuses for scripts (`flint run wait <run>` exits 3 when the run needs you). The app's own binary is the client (no window); `scripts/flint` execs it on macOS. Commands that change something are refused when an agent sends them (one Flint runs, one in a terminal tab, a known agent CLI): approving a gate stays the user's. Where the panel asks in a native dialog, the command waits for that dialog.
- **Toasts**: messages inside the window (toasts) appear in the bottom-right corner, above the status bar.
- **Notifications** (`AlertsAPI`; macOS notifications, D-Bus `org.freedesktop.Notifications` on Linux; text masked by `redact.Secrets` in Go). One model of "something needs you" (`frontend/src/lib/attention.ts`, fed by `store/alerts.ts` for the whole session, whatever panel is open) decides every notification, the badge and the in-app notice:
  - *Needs* (wait for an answer, `notifyOnApproval`, which also needs `notifyInBackground`): a chat's approval request in any turn, whoever started it (a child agent's too); an agent CLI Flint knows (`claude`, `codex`, `gemini`, `opencode`, `TERMINAL_AGENTS`, read from the foreground process) that reports *waiting* in a terminal; a native question of Flint's (`askUser`/`chooseUser`, every confirmation dialog). Each is announced once: at once when Flint is in the background, or when Flint goes there while it is still open. Go announces its own questions (`attention.go`: "Flint needs your answer" and the question's title; one asked behind another is announced when it becomes visible; one still open after 2 minutes is announced anyway, because on Linux the dialog takes the window's focus) and tells the UI with `attention:question` so they are counted.
  - Whether Flint is in front is Go's alone (`attention.go`), sent to the UI as `attention:front` (numbered; `AlertsAPI.InFront` for the start): the window's focus, asked from the window in each focus listener (`IsFocused`, since Wails runs listeners in their own goroutines and events can arrive reversed) and once after it is shown, and on macOS the app's activation (`App.followForeground`). A dialog of Flint's that appeared while Flint was in front counts as Flint, and answering one brings Flint to the front, so the dialog's own focus moves are neither leaving nor coming back.
  - Native questions don't time out: a dialog can't be closed from code, so `askNative` waits until it is answered or Flint quits, and the badge counts it until then. An asker with a deadline (an acting MCP tool's call, 5 minutes) uses `askUserCtx`: its question is not shown when the deadline passed while it waited behind another one, and a late answer to one already on screen runs nothing.
  - A terminal tab notifies at most one *waiting* and one *finished* per minute (`terminalChanged`, timestamps, no timer); its texts name the program and the folder, never the terminal's title.
  - An agent that can't start for a queue-started task (`agentStartError` from `openChat`, or an error before the agent's first output, `App.observeTaskStart`) fails that task, is told once, and holds its other queued tasks (`taskQueue.down`, shown as `TaskView.blocked`) until Start now, a change of the agents' settings, or output from a chat of that agent.
  - *Finished work* (`notifyInBackground`): an agent's turn end or error (not one of an agent with a parent: its parent is told), an agent CLI Flint knows in a terminal that is done, a run or test run, CI (`ci.notify`), a budget, Projects' automatic starts, items moving to `review` and finished clones, and what Go reports with `attention:alert` (a task whose chat did not start, a notice that did not reach its chat).
  - The badge (Dock icon on macOS; none on Linux) counts the needs still open plus finished work not seen; coming back to the window clears only the finished part. Clicking a notification brings Flint forward and shows the tab it is about.
  - In front: the Agents button's count, a *waiting* mark on a chat tab whose agent waits, and a notice "<agent> is waiting for your approval in <folder>" with **Show** when the request is not in the active tab. The notice sits under the passing toast (`.toast-stack`) and stays until answered, shown or closed.
  - With `notifyInBackground` off, a budget warning that arrives in the background is shown as a toast when you return.
  - Settings ▸ Agents ▸ Notifications shows whether they can be delivered (`AlertsAPI.Status`: allowed, not allowed by the OS with what to do, the last one not delivered, not available: no bundle, no service, the server build) and has **Send Test Notification** (`AlertsAPI.Test`). The OS permission is checked on every notification, never cached; a failure to deliver is logged once per distinct error and shown in that status.
  - A waiting project start's confirmation stays open until answered; quitting Flint while it is open records no refusal (the starter's context is done), so the next launch asks again.
- The application menu (with `Settings… ⌘,`) and the compact title bar are native Wails v3 options, with no Objective-C additions.

## Extensions

External extensions are separate programs in any language that talk JSON-RPC 2.0 over stdio and are described by a manifest (`flint-extension.json`); Flint draws their UI from data (guide: [site/guides/extensions.md](../site/guides/extensions.md), protocol: [site/extensions/protocol.md](../site/extensions/protocol.md), design: [design/extensions.md](design/extensions.md)).

- **Manage**: *Show Extensions* (palette) opens Settings ▸ Extensions: what is installed, the built-in features that can be turned off, and the repository.
- **Install**: *Install Extension from Folder…* (palette, or Settings ▸ Extensions; `flint --install-extension <dir>` from a terminal, also handed to a running Flint) copies a folder to `<config>/extensions/<id>/` after a native confirmation that shows the id, name, version, program, start mode, permissions, agent tools and sandbox. Installing the same id again replaces it, and the confirmation then starts with what changes (version, added permissions and agent tools). No marketplace, no repository-local extensions.
- **Extension index** (`internal/extensions/index`, format: [site/extensions/index-format.md](../site/extensions/index-format.md)): Settings ▸ Extensions ▸ Extension index installs prebuilt extensions from one signed index (`extensions.indexUrl`, default the release asset of flint-ide/extensions; verified with `extensions.indexPublicKey`, default the official key built into Flint, `index.OfficialPublicKey`; a build without one says "not configured" and requests nothing). *Browse Extensions* / *Check for Updates* (buttons and palette commands *Browse Extensions*, *Check for Extension Updates*) are the only things that download it: two anonymous GETs, https only, 4 MiB at most; nothing is shown before the Ed25519 signature verified. *Install…* / *Update to x.y.z…* downloads this platform's archive (size and SHA-256 from the index, 256 MiB at most), unpacks it with limits (no links, no paths outside, 10,000 entries, 512 MiB), requires the manifest's id and version to equal the entry's and then shows the same confirmation as a folder install. Installed extensions with a higher version in the index show *Update to x.y.z…*; nothing updates by itself. The verified index is cached in `<config>/extension-index/` and verified again when read. `cmd/flint-extindex` (`keygen`, `build`, `sign`, `verify`) makes an index.
- **Contributions**, under the source `extension:<id>`: palette commands (a default shortcut is dropped when the keys are taken, and the conflict is listed), sidebar panels drawn as a tree or list (lazily expanded nodes, icons from Flint's set, a click runs a command, a context menu of item actions, `view/refresh`), panels and editor tabs drawn as a table, a form or a chart (below), a Settings page generated from a small JSON schema (string, number, integer, boolean, enum, string list; values in `settings.json` under `extensions.<id>`, kept for extensions that aren't installed), status bar items, toasts (`window/showMessage`, rate-limited), files opened in the editor, `http(s)` links (asked once per site), chat drafts (`agent/ask`) and read-only agent tools on Flint's MCP server (`<short>_<name>`, can be turned off per extension).
- **Tables, forms and charts** (`"view": "table" | "form" | "chart"` on a panel or a tab view; `capabilities.views` and `charts` in `initialize`): Go decodes the answer to `view/resolve`, types it and cuts it to its limits before the web view gets it, and text is drawn as text. A *table* has up to 30 typed columns (text, number, date, badge with a severity from the theme) and 5,000 rows, virtualized; a click on a header sorts the rows in Flint (ascending, descending, the extension's order; numbers and dates by value, empty cells last), `↑`/`↓`/`Page Up`/`Page Down`/`Home`/`End` move the selection, `↵` or a double click runs the row's command, a right click or `Shift+F10` opens its actions (`view/action`), `⌘C` copies the row and **Copy** the shown rows as TSV. A *form* has up to 50 fields with the settings schema's types and checks plus `required`, `multiline`, `secret` and `placeholder`; the values are checked in the page and again in Go against the fields last drawn, and only then sent as `form/submit`, whose answer may carry per-field errors, a form error and a message. A secret field never receives a value from the extension and its text is kept nowhere by Flint. A *chart* is a line, bar or area chart of up to 10 series of 2,000 points over a number, date or category axis, drawn as SVG with series colors from the theme, a legend, and its values as a table under **Values**. Tab views of these kinds are opened with `window/openTab`, resolved with the tab's key and data, refreshed per tab (`view/refresh` with `key`) and restored with the session when the manifest says `restore`. `markdown`, `cards` and `stack` views are not drawn: a manifest with one is refused.
- **Editor decorations** (`contributes.decorationSets`, needs `workspace.read`): an extension marks lines in open files with gutter markers, wavy underlines with a hover message, dim text after a line and highlights, colored by severity from the theme. Each set names its files by language, extension or name glob. Flint sends `editor/opened`, `editor/changed` (debounced 300 ms, with a document version) and `editor/closed` only for matching files in trusted folders that `workspace/readFile` would return (never `.git` or credential files), with unsaved text only for sets that declare `unsavedText`; the extension answers with `editor/setDecorations`. A publish for an older version is dropped, positions are clamped, at most 5,000 decorations per set and file, and marks move with edits until the next publish. A decoration's actions are quick fixes (hover buttons, a click on the gutter marker, or *Show Extension Quick Fixes*, `⌥⇧↵`): `editor/action` returns text edits applied as one undo step only if the version still matches, or the action runs one of the extension's commands. Each set has a switch in Settings ▸ Extensions and a *Toggle … in Editors* command (`extensions.decorations` in `settings.json`); *Toggle Extension Decorations in This Editor* hides them in one editor. Opening a matching file starts the extension, an open decorated document keeps it from the idle stop, and its decorations are removed when it stops, crashes, is turned off or is uninstalled.
- **Lifecycle**: nothing is read before the window is up and nothing runs until an extension is used (or declares `onStartup`); `initialize` handshake with contract version check; idle stop after 5 minutes; restart after a crash with a 1 s / 4 s backoff, stopped after 3 crashes in 10 minutes until *Restart*; request timeouts (5 s views, 30 s commands, 120 s tools); 4 MiB message cap; process-group kill on stop, turn-off, uninstall and quit.
- **Security**: only trusted folders are passed or readable; `workspace.read`, `secrets` and `agent.ask` are enforced on every request (`-32001` otherwise); `.git` and credential files are never returned; secrets live in the keyring (`flint-extensions`, `<id>:<key>`); the process gets a minimal environment; declared network hosts are shown, not enforced.
- **Sandbox**: an extension whose manifest has `run.sandbox` runs confined by the operating system: Landlock (files; TCP, signals and abstract sockets on newer kernels), a seccomp socket filter and `no_new_privs` on Linux, applied by Flint re-executing itself as a launcher; `sandbox-exec` with a generated profile on macOS. The strict profile (`"sandbox": {}`) reads the extension's folder, system files and, with `workspace.read`, the trusted folders; writes only its data folder and a private `TMPDIR`; has no sockets; runs only its own program. The manifest adds `read` and `write` paths (`~/…`, `${XDG_…}`, `${env:NAME}` for a `run.env` variable), `network`, `localSockets` and `exec`, or declares `"mode": "none"`. Never granted: Flint's own folder, paths that contain protected locations (`~/.ssh`, `~/.aws`, `~/.kube`, browser profiles, keyrings, shell history, …), protected locations not named by the manifest. Sandboxed processes get no core dumps and at most 4,096 open files; memory and CPU are not limited. A manifest without `run.sandbox` runs unconfined. The install dialog, the extension's card, its log and `flint-extcheck` show the state: *Sandboxed* with what it may read, write and reach (and what the system can't enforce: an older kernel), *Not sandboxed (declared by the extension)*, *Not sandboxed: the extension doesn't declare a sandbox*, or *Not sandboxed: not available on this system (reason)*. **Only run sandboxed extensions** (`extensions.requireSandbox`, off by default) refuses to start the unsandboxed ones. A sandboxed extension with `workspace.read` is restarted when the trusted folders change. Repository-local extensions remain unsupported.
- **Settings ▸ Extensions**: each extension's state (not running, running, crashed, stopped after crashes, off, broken), version, program, permissions, sandbox, agent tools, warnings and shortcut conflicts; an on/off switch, *Show Log* (stderr, log messages and lifecycle, last 256 KiB), *Restart*, *Uninstall…* and *Reload*.
- **Color themes** (`contributes.themes`): interface, editor and terminal colors, checked with the custom theme rules (Flint's color names, hex values) when the manifest is read. An extension with only themes has no program and runs no code. A theme is chosen under Appearance ▸ **Color theme** or with **Use …** on its card, and copied into `customTheme`, so it stays after uninstalling.

## Diagnostics

- Flint writes its own log to `~/Library/Logs/Flint/flint.log`. It is rotated at 5 MB (one old file is kept), secrets and the home path are redacted, and the file mode is `0600`.
- Frontend errors (uncaught exceptions, rejected promises, render errors) and Go panics are logged.
- **Tool check** (**Help ▸ Check Tools…**, "Check Tools…" in the command palette, or the link on the Welcome screen) lists the external tools Flint drives, grouped (essentials, AI agents, languages and debugging, containers and cloud): a status dot, the version found or "Not installed", the feature each one enables, a link to its documentation page, and for missing tools an install command with a **Copy** button (Homebrew where there is a formula, `go install` for gopls and Delve, `rustup` for rust-analyzer). Language servers with alternatives count as installed when any one is found (vtsls or typescript-language-server; basedpyright, pyright or pylsp), and the row says which. A tool that is on `PATH` but whose version command fails (for example a rustup proxy without the rust-analyzer component) shows as "Not working" with its error. Only Git is required. **Recheck** runs the check again.
  - It opens by itself once, on the first launch (remembered in `state.json` as `toolCheckShown`).
  - The check waits for the login-shell `PATH`, then runs only fixed version commands (`--version` or equivalent), in parallel with a 5-second timeout, in the home folder and never in a workspace folder, so a repository's `.tool-versions`, `rust-toolchain.toml` or `.nvmrc` can't choose what runs. The Pyright language servers have no version flag and are not run at all. Nothing is installed by Flint.
  - One table in `internal/tools` feeds both the tool check and the bug report; language-server binaries come from the LSP server specs.
- **Help ▸ Report an Issue…** opens a prefilled GitHub issue in your browser and copies the full report to the clipboard. The report contains the versions of Flint, macOS, Go and Wails, the versions of the tools in the tool check, and the last 150 log lines, all redacted. You review the issue before submitting it.
- **Help ▸ Copy Diagnostics** copies the same redacted report to the clipboard.
- **Help ▸ Show Logs in Finder** reveals the log file in Finder.
- There is no telemetry. The only requests Flint makes on its own are the update check and the release notes below.

### Update check

- Flint asks GitHub's API for the latest release (`GET https://api.github.com/repos/flint-ide/flint/releases/latest`): one anonymous request with `User-Agent: Flint/<version>`, no token, cookies or identifiers, a 10 s timeout and a 1 MB response limit (`internal/update`).
- Automatically: 5 s after launch and then once a day while Flint runs, at most once every 24 hours (the last check, its answer and a skipped version are kept in `state.json`, so a restart reuses the answer instead of asking again). Never in development builds (`dev`, `dev-<sha>`), and never when `checkForUpdates` is off (Settings ▸ Updates). A failed check is only logged.
- The running version (`vX.Y.Z` from `-ldflags`) is compared with the release tag by Flint's own SemVer compare; a pre-release sorts below its release.
- A newer release shows a notice in the status bar: **Download** opens the release page in the browser (only a `https://github.com/flint-ide/flint/…` link from the API; anything else falls back to the releases page), **Skip This Version** stays quiet until a later release, **✕** hides it until the next launch.
- **Help ▸ Check for Updates…** (also in the palette and Settings ▸ Updates ▸ Check Now) checks immediately, ignoring the daily limit and the setting, and says "You're up to date (vX.Y.Z)" when there is nothing new.
- **What's New**: the first launch of a newer version opens a "What's New in vX.Y.Z" tab with that release's notes, grouped into New Features, Bug Fixes and Other Changes. Items link to their pull requests, and the header links to the release page on GitHub. The notes come from the GitHub Release of that tag (one anonymous GET, under the same rules as the update check). They are sorted by Conventional Commits type: `feat` goes to New Features, `fix` and `perf` to Bug Fixes, and everything else to Other Changes.
- The tab is not shown on a fresh install, in development builds, or when `checkForUpdates` is off, and then Flint does not ask GitHub for the notes at all. The version that ran last is kept as `lastSeen` in `state.json`.
- **View Release Notes** (palette, category Help) opens the notes of the running version at any time.
- Flint never downloads or installs anything: there is no auto-update framework.

## Restricted Mode (workspace trust)

A folder opened for the first time is untrusted until you click **Trust Folder** in the banner (or run "Trust Folder" from the command palette). A downloaded archive or a fresh clone can carry configuration that runs programs, so in Restricted Mode Flint:

- does not auto-start a terminal (shell prompts run `git status` and version-manager hooks that read the folder);
- does not start language servers that execute the folder's code: rust-analyzer (build scripts, proc macros, `.cargo/config` tools), the Python servers (they run the virtualenv interpreter the folder points at) and any server set in Settings that Flint doesn't know. They start as soon as you trust the folder; extra language-server arguments from Settings are ignored until then;
- runs agents (chat, commit messages, reviews, conflict resolution) without the folder's agent settings and hooks (Claude Code gets `--setting-sources user`, because `-p` mode skips its own trust prompt) and without the extra agent arguments from Settings;
- does not start custom ACP agents at all (chat or commit messages): Flint can't tell them to ignore the folder's configuration, so the error asks you to trust the folder;
- lists the folder's `.flint/prompts` marked "untrusted repo", and never lets them replace a built-in or personal prompt of the same name;
- loads no repository agent definitions (`.flint/agents`) and only counts them, so Settings ▸ Agents can say how many were ignored;
- refuses the Projects feature's **Delegate** for a repository checkout in the folder (reading a project is not restricted), so no agent starts there until you trust it; a project in the folder is left out of `get_project`, refused by Plan with Agent…, Add Project Context… and `add_project_item`, and Delegate of its items (also a waiting start, with its own wording) asks first in a native dialog that shows what will be sent, its `PROJECT.md` included; its agents get only what that dialog showed; a joint group needs every repository and worktree trusted; a clone into an untrusted folder is untrusted until trusted, and a clone into a trusted folder (trusted at once) is refused for an untrusted project and announced for a trusted one;
- runs Git without hooks, even on commit and push (`core.hooksPath=/dev/null`).

Regardless of trust:

- Git never runs repository-defined clean/smudge filters, textconv drivers or fsmonitor for Flint's own git calls (status, blame, diff); filters from your global config, such as Git LFS, still work;
- typescript-language-server only starts when it can be pinned to its own TypeScript, never the folder's `node_modules/typescript`;
- a `.http` request can only send body files (`< file`) from inside the open folders;
- the Markdown preview doesn't load remote images until you click "Load remote images" (no tracking pixels);
- database TLS verifies the server certificate and host name; "Don't verify certificate (insecure)" is an explicit opt-out for private CAs;
- credentials are removed from terminal scrollback before a session is saved.

Trusted folders (and their subfolders) are remembered in `state.json`; "Revoke Folder Trust" in the command palette turns Restricted Mode back on.

## Command palette

The command palette (`⇧⌘P`, like "Find Action" in IntelliJ) fuzzy-searches every command in the app (navigation, workspace, projects, workflows, git, GitHub, terminal, agent, run, profiling, databases, scratchpads), shows each command's category and shortcut, and keeps recently used commands at the top.

Commands and global shortcuts come from a single registry (`frontend/src/lib/commands.ts`). A new feature adds its actions with `registerCommand`.
